DMP corrective-data PoC: method and maths

2026-10-14 · session impl21, scope from prim (user, 10-14) · source design: ROOT_TO_GOAL_CORRECTIVE_DEMOS (approved 10-12, incl. res's 10-14 additions) · for the user's approval · no code yet

Status: method for approval. No code has been written and nothing has been run. The only numbers on this page that are not from other docs are a read-only look at the R-047 logs used to pick candidate scenarios (§6); they are exploratory and UNVERIFIED. Everything the PoC produces goes to val before it travels.

0 · Bottom line

  • What the PoC does: for 4 scenarios from R-047, restore the sim at the failure's root, pick the 3 nearest clean human demos, bend each demo's remaining motion from the root to the goal with a DMP, execute it in LIBERO through the normal OSC controller, and keep it only if the task succeeds and the motion passes a jerk check. Then run the same thing over all R-047 failures to see where it works, by failure type and by distance from the demos.
  • Choices I recommend: one Cartesian position DMP per demo segment in the Hoffmann/Pastor 2009 form (it cannot flip or overscale; it differs from the source design's vector-wise scaling, see §1.3 and decision C1), orientation as a rotation-vector DMP relative to the goal orientation (the rotations here are small), the gripper replayed as a binary step at segment boundaries, and segments expressed in the frame of the object they act on.
  • Fastest because: everything except a few visual-check renders runs on CPU, physics only. Roots are restored by replaying the logged actions, not by re-running the policy. No GPU, no training, no IDM.
  • Effort: about 4 working days of my time plus val's check (§9). The source design estimated 5–8 days for S0–S6; the saving comes from what §10 skips.
  • Biggest risks: (1) restoring a root by action replay may not reproduce the logged state (it has to be tested first, B1); (2) nominal demos never show a recovery, so a far root may be outside anything a demo segment can bend to (that is what the coverage-gap measure and scenario D test).

1 · DMP formulation

1.1 · Space and segments

  • Cartesian EEF space, not joint space. The actions we record and the policy's action space are both relative EEF deltas (OSC_POSE, control_delta), so a Cartesian reference turns directly into actions. Joint space would need IK and would not transfer between start poses that differ in the joints (which is exactly what R-047 perturbs).
  • Segments split at gripper events. Each LIBERO-Spatial demo has two gripper events (close, open), so three segments: A approach → grasp pose (frame: target bowl), B lift, carry → release pose (frame: plate), C retreat (frame: plate; usually not needed because success fires on release).
  • Object frames. Each segment's goal is the demo's segment-end EEF pose expressed in its object's frame, then mapped to the current object pose in the root scene. This is MimicGen's object-centric idea; only the goal is transformed, the shape is the DMP's job. As built (10-14): the frames are translation-only, because the bowl and the plate are rotationally symmetric: the goal is the demo's EEF-minus-object offset placed at the object's current position, with the demo's world orientation. This replaces the "yaw closest to the root's" rule in §1.4.

1.2 · Position DMP (per axis, per segment)

Discrete DMP in the Hoffmann/Pastor form (Hoffmann et al. 2009; Pastor et al. 2009), one per axis of the EEF position y ∈ ℝ³:

canonical:        τ ṡ = −α_s s                          s(0) = 1
transformation:   τ ż = K (g − y) − D z − K (g − y₀) s + K f(s)
                  τ ẏ = z
forcing term:     f(s) = Σᵢ wᵢ ψᵢ(s) · s / Σᵢ ψᵢ(s),     ψᵢ(s) = exp(−hᵢ (s − cᵢ)²)

constants (standard): K = 150 (τ-normalised), D = 2√K (critical damping),
                      α_s = −ln(0.01) ≈ 4.6 so s(τ) = 0.01, N = 30 basis functions,
                      cᵢ spaced evenly in time (cᵢ = exp(−α_s·i/(N−1))), hᵢ = 1/(cᵢ₊₁ − cᵢ)²

Fitting on a demo segment with samples y_d(t), t = 0…T at 20 Hz, τ = T·Δt:

z_d = τ ẏ_d,   ż_d = τ ÿ_d          (finite differences, demo smoothed with a 5-step Savitzky–Golay filter)
f_target(s) = (τ ż_d + D z_d) / K − (g_d − y_d) + (g_d − y_d,0) · s
w = argmin Σₜ (f(sₜ) − f_target(sₜ))²     (locally weighted regression, one closed-form solve per basis)

Why this form. The original form multiplies f by (g − y₀). When the demo's displacement on an axis is small (common: the approach is mostly vertical at the end), a new start flips or overscales the shape on that axis. In the 2009 form f is in absolute units, so the shape is kept as the demo had it, and the −K(g−y₀)s term shifts the whole path linearly from the new start to the new goal as s decays. For a correction this is what we want: "the demo's motion, plus a smooth shift that absorbs the root's offset". It cannot flip and cannot overscale.

1.3 · Against the source design's vector-wise scaling

The source design (S4) names a Cartesian DMP with vector-wise scaling (rotate and scale f so the demo's displacement vector maps onto the new one; Ginesi et al., Sidiropoulos & Doulgeri). That fixes flipping but still scales the shape by ‖g−y₀‖/‖g_d−y_d,0‖. For roots far from the demos (10–40 cm against demo approach segments of a similar length) that scale reaches 2–3×, which stretches the lift height and the approach curvature by the same factor. I recommend the 2009 form as the default and vector-wise scaling as a second arm in the scenario runs only (it is ~20 extra lines). Decision C1.

1.4 · Orientation

  • Represent orientation as the rotation vector relative to the segment's goal orientation: r(t) = log(q_g⁻¹ ⊗ q(t)) ∈ ℝ³, and run the same DMP as §1.2 on r with goal 0. Convert back with q(t) = q_g ⊗ exp(r(t)).
  • This is exact as a parameterisation and well behaved while ‖r‖ stays well below π. LIBERO-Spatial grasps are near top-down; the largest per-step rotation command in a demo I checked is 0.35 of full scale (≈ 0.17 rad/step). The build checks max ‖r‖ over all 500 demos and roots; above 60° it falls back to the quaternion DMP of Ude et al. 2014 (with the 2019 SO(3) correction). Both cost about the same to write; the rotation-vector form is easier to test and to explain.
  • The goal orientation q_g is the demo's segment-end orientation in the object frame, mapped to the root scene. Bowls are rotationally symmetric, so for segment A the yaw about the bowl's vertical axis is free: take the yaw closest to the root's current yaw (avoids needless wrist spins).

1.5 · Gripper

  • The demos command the gripper as binary ±1. Within a segment the command is constant; at the segment end it switches, exactly as in the demo. No gripper DMP.
  • After a close or open command, hold the arm's reference still for the number of steps the demo took between its gripper command and the start of its next motion (read from that demo), so the fingers settle before lifting.

2 · Retargeting maths (from root to goal)

Given root state at step t_r, with EEF pose (y_r, q_r), EEF velocity ẏ_r, gripper state, object poses.
Given matched demo d at step t* inside segment k (see §4).

1. Remaining demo motion:  segment k from t* to its end, then segments k+1, … unchanged.
2. Goal of segment k:      g = T_obj(root) · T_obj(demo, end of k)⁻¹ · y_d(end of k)
                           (object frame of segment k; T = object pose as a rigid transform)
3. Fit the DMP on the demo's sub-segment [t*, end of k]  (so its shape starts where the root is most similar).
4. Integrate with y₀ = y_r, z₀ = τ·ẏ_r (velocity-matched join, §3), goal g, τ = (end − t*)·Δt.
5. Segments k+1, …: y₀ = where the previous segment actually ended (achieved pose, not planned),
   z₀ = τ·(achieved velocity), goal from their own object frames. Each is fitted on its full demo segment.
6. Output: a reference EEF pose per 20 Hz step plus the gripper schedule.

τ keeps the demo's duration for the sub-segment. If the root is much further from the goal than the demo point was, keeping τ means a faster motion; step 4 checks the peak reference speed against the demos' 99th percentile and, if it is exceeded, stretches τ by the ratio (the DMP is time-invariant in shape, so this only slows it).

2.1 · The baseline arm: I-Gen-style linear bridge

Same match, same goal. Instead of a DMP: rigidly transform the demo's remaining segment into the root scene's object frame, then linearly interpolate the EEF from the root pose to the transformed segment's first pose over 20 steps, and replay. This is the comparison the source design asks for (§4a there): the DMP has to beat it to earn its place.

3 · Velocity-matched join

  • Position: continuous by construction (y₀ = y_r).
  • Velocity: start the DMP with z₀ = τ·ẏ_r, where ẏ_r is the EEF velocity at the root (finite difference of the logged EEF positions over the last 2 steps, cross-checked against the sim's site velocity after restore). The demo's own start velocity is replaced; the difference decays through the damping term with time constant τ/√K ≈ 0.08·τ, i.e. 4–8 steps for typical segment lengths.
  • Acceleration: not matched. At s = 1 the DMP's acceleration is (K f(1) − D z₀)/τ², which generally differs from the policy's acceleration at the root, so jerk can spike at the join. I propose to measure it (§5.2) rather than add C² matching up front. If the jerk check fails often, the fix is a 3-step quintic blend on the reference, about half a day.
  • If the root is the start of a corrective move against the policy's motion (for example the policy was moving away from the bowl), velocity matching makes the correction start by continuing that motion for a few steps. That is the honest join (it is what the robot is doing), but if it makes too many rollouts fail, z₀ = 0 is the alternative arm. Measured in B4.

4 · Choosing a matching demo

Candidates:  the 50 demos of the same task (same scene layout family), same segment k as the root.
             Root's segment: A if the target is not held and no grasp attempt has completed; B if held.
Features at a step (all in the segment's object frame):
   p   EEF position relative to the object               (3)
   φ   EEF orientation as rotation vector relative to the object, yaw folded for segment A   (3)
   v   EEF velocity                                     (3)
   w   gripper aperture                                 (1)
   (segment B adds the held object's offset from the EEF (3))
Distance:    d(root, demo step) = ‖(x_root − x_demo) / σ‖₂,  σ = per-feature std over all demo steps of
             that segment in that task. Velocity weighted 0.5 (it is noisier).
Match:       for each demo, the step t* minimising d; keep the 3 demos with the smallest d (top-k = 3).
  • Single-frame match plus velocity, not a 5–10 step window. The window in the source design is meant to capture motion context; the velocity term carries most of it, and the window is what makes matching expensive. Logged as a skip in §10.
  • Coverage gap. Reference spread: for each demo step, its distance to the nearest step of any other demo of the same task and segment (leave-one-demo-out). d_gap = 95th percentile of that. A root whose best match has d > d_gap is a coverage gap. It is still executed (we want to know whether the DMP bends that far), but it is reported separately. The source design's planner fallback for gaps is not built (§10).
  • DART-style offsets (source S3, res 10-14): for each root, also 5 restarts from small random EEF offsets (uniform direction, radius 1–3 cm, reached by a short OSC move from the root), each matched and executed the same way. They give extra labelled off-distribution states near the root. In the PoC they run in the sweep (B5), not in the first scenario runs.

5 · Executing and judging a rollout

5.1 · Execution

  • Root restore. The R-047 logs keep EEF, joints, gripper and object positions per step, but not the full MuJoCo state. So: rebuild the same LIBERO-Plus env (task, init state 0, the same start-pose perturbation spec), reset, and replay the logged actions for steps 0 … t_r − 1. Accept the restore only if EEF position and every object position match the log within 1 mm at every replayed step. Physics is deterministic given the same state and actions; the known render nondeterminism (README risks) concerns images, not physics. This is test B1 and it gates everything else.
  • Where the root sits. For a grasp root the restore point is the step at which the faulty close is commanded, before it takes effect (fingers still open). For a release root it is the step before the open command (bowl still held). The correction therefore never has to undo a gripper action.
  • Tracking. Each step, command a_pos = clip((y_ref[t+L] − y_now)/0.05, −1, 1) and a_rot = clip(log(q_ref[t+L] ⊗ q_now⁻¹)/0.5, −1, 1), gripper from the schedule. 0.05 m and 0.5 rad are the OSC_POSE output limits in the demo files' controller config (kp 150, critically damped). The look-ahead L (1 or 2 steps) is tuned once in the self-reproduction test (§7, T2) and then frozen.
  • What is recorded. The commanded 7-D actions, which are in the env's action convention (the same one our harness sends for GR00T), plus the per-step state. Frames are rendered afterwards only for the kept rollouts we look at, by replaying their actions on the GPU through prim.
  • Budget. At most 200 control steps after the root, with no cap at the episode's original 280-step limit (user, 10-14, C3). Each kept episode logs whether it would also have fitted inside 280, so it can be used as a full episode or as a root→goal segment only.

5.2 · Judging

CheckRuleWhy
SuccessThe env's own success check (BDDL predicate: target bowl on the plate) fires within the budget.The same check the eval uses. Full-task success, not a phase-only predicate (decision C2).

Pass if it is ≤ the 99th percentile of the same statistic over all 16-step windows of the 500 human demos.Training data with a spike at the join would teach the policy that spike. A rollout is kept only if all four pass. Each reported yield says which checks failed, so "fails success" and "succeeds but jerky" are told apart.

8 · "Applies to most failures?" analysis

  • Population: all 176 failed R-047 rollouts: 112 on the start-pose axis (109 perturbed + 3 at radius 0) and 64 on the camera-yaw axis (61 perturbed + 3 at yaw 0). The earlier "109 vs 112" was only whether the radius-0 rows count; both numbers are right (reconciled 10-14 from the axis manifests).
  • Roots: a minimal rule set, the same events ROOT_IDENTIFICATION §3 lists: grasp onset → miss or slip by bowl lift; held then lost away from the goal → drop; released with the bowl > 3 cm from the plate centre → off-target; no grasp before timeout → stall. Both root rules (first event, first unrecovered) are run, so every failure gets up to two roots. C4 (user, 10-14): reuse the rules in experiments/poc_toy_instance.py / the UQ10 probe for now, tagged UNVERIFIED like the rest, because the PoC only needs the root step, not a validated label. The user wants a more robust root-selection process; that is open work (UQ4), not part of this PoC.
  • Per root: top-3 matches, DMP arm and linear arm, plus 5 DART offsets on the DMP arm. A root counts as covered if at least one of its 3 matched DMP rollouts is kept.
  • Coverage-gap measure: d_match / d_gap (§4), the root's best match distance in units of the demos' own 95th-percentile neighbour distance. Binned ≤ 1, 1–2, 2–4, > 4.
  • Tables reported:
    1. Kept rate by failure type (phase × mode) × root rule.
    2. Kept rate by coverage-gap bin, and by start-pose radius / camera yaw.
    3. DMP vs linear bridge on the same roots: paired counts (both kept, only DMP, only linear, neither), McNemar.
    4. Which check fails when a rollout is not kept (success, jerk, speed, collateral).
    5. DART offsets: kept rate per offset radius.
  • Reading the answer: "applies to most failures" means the covered fraction is above one half overall and does not collapse in any one failure type that holds more than 10 % of the failures. If coverage drops sharply beyond some gap bin, that bin is where real teleop (or the planner fallback) is needed, and the PoC says how many failures sit beyond it. All of these numbers are UNVERIFIED until val passes the code.
  • Caveat on camera failures: their start state is nominal, so their roots are probably close to the demos and should be easy for the DMP. They are reported separately so they do not inflate the start-pose answer.
