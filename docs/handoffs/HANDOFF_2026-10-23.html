3 · Findings and current recommendation

  • No tool does this as is. The closest is EmbodiedGen (Apache 2.0; image → 3D → MJCF, with VLM-estimated scale, mass and friction) [V], but it gives a lookalike from one image, and its local backbones need ≥16 GB.
  • Shared recipe of the best-scoring real-to-sim systems (PolaRiS r≈0.9 on DROID, SimFoundry r≈0.91) [V]: segment → generate the full shape (TRELLIS) → mesh for physics → camera appearance handled separately (splats or baked real views).
  • GPU limit: our RTX PRO 1000 laptop GPU has 8 GB [M]. TRELLIS needs ≥16 GB, TRELLIS.2 ≥24, SAM 3D Objects ≥32 [V]. Fits: TripoSR (MIT), Stable Fast 3D (Stability Community Licence), Hunyuan3D-2 shape-only (licence excludes EU/UK/South Korea), each ~6 GB [V].
  • MuJoCo's native renderer ignores PBR; only texture, scalar specular/shininess, reflectance on planes and boxes [V]. Fuller materials only via the Blender path (blender_render.py).
  • Recommendation, C1 [I]: generate the shape (≤8 GB model), scale and ICP-align it to our stereo points, texture every seen side by projecting our wrist and exterior frames (Open3D colour map optimisation, MIT), keep generated texture only on the unseen side → CoACD → --object_props. Lookalike fallback: uCO3D (CC BY 4.0, ~170k 360° videos, has a vegetables_and_legumes super-category [V]; a radish category is unchecked).
  • Ground-truth caveats: the c3 apple is probably not YCB 013_apple: the mask is 5.9 cm wide vs YCB's 7.2–7.5 cm (AssetPack's measurement) [V]. Whether the real bowl is the GSO Akita product is unchecked. The radish is detected in only 1 of 5 sampled wrist frames (f45) in runs/real2sim/ep_c3_stereo/wrist_anchors.json [M]. Full coverage still to measure (moved into the PoC).

DMP (filled 2026-10-23 11:50 by DMP)

owner: DMP · DMP corrective-demo proof of concept, taken over from impl21 (gone since 10-14) via prim on 10-19. No new code or runs since the handover. The code is committed; every number is UNVERIFIED (val has checked none of it).

1 · What the PoC is

  • GR00T N1.7 fails a LIBERO-Spatial episode (R-047). We find the failure's root step, restore the sim there exactly (reset, then replay the logged actions; ≤ 1 mm check at every step), find the 3 nearest human demos, bend each one's remaining motion with a DMP (Hoffmann/Pastor 2009, absolute-units forcing term; goal in the object frame), execute it with the OSC controller, and keep it only if it passes four checks: success, jerk, speed/saturation and collateral (no other object moved > 2 cm). The kept rollouts are corrective training data. Origin: the user's idea in docs/ROOT_TO_GOAL_CORRECTIVE_DEMOS.html.
  • Arms compared on the same matches: dmp, dmp_vector (vector-wise scaling), dmp_rest (starts from zero velocity) and linear (IntervenGen-style 20-step straight bridge, then the demo replayed rigidly).
  • Demo search (match.py): a single snapshot plus velocity, nearest neighbour. Candidates are the human demos of the same task, at steps in the same phase (A approach / B carry). Features are object-relative and taken from the exact sim state:
    • A, 10 numbers: hand − bowl (3), hand rotation vs the demos' mean rotation (3), velocity (3, weight 0.5), finger gap (1).
    • B adds hand − plate and bowl − hand.
    Each feature is divided by its standard deviation over the demos. For each demo the closest step leaving ≥ 20 steps of the phase is taken; the top 3 demos are used. Coverage = distance / d_gap (95th percentile of the leave-one-demo-out nearest-neighbour distance between demos).
  • Phases:
    • Demos are cut at gripper-command changes (blips of 1–2 steps absorbed). The "final grasp" is the last close that lifts the bowl ≥ 5 cm and is followed by a release; earlier attempts are only tagged (regrasp, replace, …).
    • The root's phase comes from its event type: miss, slip, wrong object, never reached and drop → A; off-target place → B. Restore points are chosen before the gripper action takes effect.
  • Explained to the user 10-19: the search uses privileged sim state (exact object poses, target identity from the BDDL). This is fine for generating sim data; it matters for real-robot use.
