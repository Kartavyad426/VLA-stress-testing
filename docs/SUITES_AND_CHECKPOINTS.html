Suites, checkpoints and cross-task robustness

Written 2026-09-28. The question: all our GR00T robustness work runs on one LIBERO suite with a suite-specific fine-tune. Could we evaluate more general policies across more tasks, and would the harness and the localisation methods carry over? Sources for every claim are listed in §9.

today

GR00T: 1 suite, 10 tasks

2,712 rollouts, all on libero_spatial with the spatial-only fine-tune. The other 30 tasks have only MINERVA and SmolVLA runs.

why fine-tunes

Base VLAs aren't benchmark-ready

Every published LIBERO number is a LIBERO fine-tune, and our roster rule needs a published number to reproduce.

general option

One checkpoint, all 40 tasks

MINERVA already does this and reproduced (R-016). π0.5 does too, but needs a bigger GPU.

harness

Knobs carry over; methods need work

The perturbation knobs are suite-agnostic. Localisation needs goal-based scoring for goal tasks and stage awareness for libero_10.

3 · Why fine-tuned checkpoints

  • A base VLA isn't set up for LIBERO's robot. Base models such as nvidia/GR00T-N1.7-3B (cached locally) are pretrained on many robots. Before running on a given setup they are post-trained on its robot, its cameras (LIBERO: agent view plus wrist), its control mode and rate (delta end-effector pose at 20 Hz) and its action normalisation. Every published LIBERO number, for GR00T, π0/π0.5, OpenVLA, SmolVLA or MINERVA, comes from a LIBERO fine-tune.
  • Our roster rule needs a published number. A policy stays on the roster only if it reproduces its published result; that is why SmolVLA was vetoed. As far as we know, the base checkpoints have no published LIBERO number (not verified exhaustively). Without one we cannot tell a weak model from a harness bug. MODELS_AND_COMPUTE.md §R1 gives an example: a hand-translated config means guessing normalisation statistics, which "can manufacture apparent model failures".
  • What a fine-tune still tells us. Robustness here means "how far from its training distribution does this trained policy hold up". That is a fair question for a behaviour-cloned policy (RESULTS "Current state" item 3). Its answer carries over to the base model only in part: a fine-tune inherits the backbone, not the base model's behaviour.

6 · Do the localisation methods carry over?

By localisation we mean the methods that ask where a perturbation enters and whether it can be undone:

  • the backbone-signal captures (R-037);
  • the pathway splice, i.e. image versus state tokens (R-039);
  • the wrist-versus-agent camera split (R-042);
  • first-chunk rescue (R-044, R-048, R-050, R-051).

They work on the model's inputs, so in principle they are suite-agnostic. Four things need changing:

  1. Goal tasks with no object to carry. For "open the middle drawer", "turn on the stove" and "push the plate", the closest-approach metric (r039_run.py:136, basis "targets" or else "all_objects") has no meaningful target. These tasks need progress measured against the goal condition in the task's BDDL file instead.
  2. libero_10's two stages. A corrected first chunk tests only the start of stage 1. Localisation has to be stage-aware, with stage labels taken from each task's goal conditions via _gt_scene_object_pos. R-043 already designs this, including a check that failures cluster at stage transitions.
  3. Language will behave differently. In spatial the instruction only picks out which bowl. In goal it is the only cue. So R-038 (empty prompt, 50/100) and R-049's language rows are predictions to test on the other suites, not results that transfer.
  4. Paired references. Every splice run pairs a perturbed episode with a nominal one on the same scene. That needs the unperturbed control per checkpoint (see §5, Baselines).

7 · Cost and recommended order

  • GR00T reproduction runs for object, goal and libero_10: about 1 h each at 10×10 (estimate; GR00T rollouts run ~20–35 s in R-029/R-047).
  • A failure hunt the size of R-026 (~600 L4/L5 variants): one overnight run per suite.
  • R-043 as designed (500 nominal + 1,228 variants + repeats): several days of GPU.

The GPU queue already holds R-052 (~9.5 h) and SFT's R-053–R-056, whose order is waiting on the user.

  1. MINERVA failure hunt on object and goal, R-026 style. It needs no new model and no new reproduction run, and it shows whether goal's no-object tasks need item 6.1 fixed first.
  2. GR00T reproduction runs for the three other checkpoints. Cheap, and they decide whether option A is usable.
  3. Then choose between R-043 (libero_10, mechanism) and GR00T object/goal failure hunts (coverage).
  4. π0.5 on a rented GPU if one policy across 40 tasks is the goal and MINERVA is too weak to stand in.
