1 · Goal

Make eval tasks by prompt on top of a reconstructed scene. The reconstructed episode is the reference: table, background, lighting, cameras and robot rig come from real footage and stay as they are. New objects and tasks are composed in simulation, and the physics simulator decides what fits where. Example (user, 10-28): "a scene like drawer having 5 blocks inside and robot has to take them out and stack them color wise".

The final goal is an eval set: each created task has a success rule, is shown solvable by a scripted expert, and passes the scene checklist (REAL2SIM_CHECKLIST_V1.html, sections B, D, E) before the user approves it.

2 · Architecture: two layers

LayerWhatTestable without a model?
1 · Scene config + scene API (Python)A JSON config per created scene, and ~6–8 functions that read and change it, with the physics simulator answering every placement questionYes: scripted calls in tests; later the user through the inspector
2 · Agent (local model via Ollama)Turns a prompt into tool calls on layer 1; reports what it did, any resizing, and anything infeasible—

Layer 1 is model-agnostic: functions with JSON schemas. Any model with tool calling can drive it; the agent is a thin adapter.

3 · Scene config

One file per created scene. Base objects come from the reconstruction and are locked; added objects carry where they came from and any change the agent made. This is the same mechanism as the planned scene overrides file (SCENE_V1_MECHANISMS B8), extended: manual edits in the inspector, perturbations and the agent all write it.

{
  "base_scene": "runs/real2sim/ep_orange_block_stereo",      // reconstructed scene (read-only)
  "base_objects": {                                          // from scene_fit.json, LOCKED
    "orange_block": {"locked": true, "source": "reconstructed"},
    "black_bowl":   {"locked": true, "source": "reconstructed"}
  },
  "added_objects": {
    "drawer_1": {"source": "libero:short_cabinet", "pose": [0.55, -0.20, null, 90],   // x, y, z (null = on the table), yaw deg
                 "scale": 1.0},
    "red_block_1": {"source": "primitive:box", "size_m": 0.030, "rgba": [0.8, 0.1, 0.1, 1],
                    "relation": {"inside": "drawer_1/drawer_middle"},
                    "resized_from_m": 0.040, "resize_reason": "did not fit inside drawer_middle at 0.040"}
  },
  "task": {"instruction": "take the red block out of the drawer and put it in the bowl",
           "success": {"type": "inside", "object": "red_block_1", "target": "black_bowl"}},
  "checks": {"settle": "pass", "expert": "pass", "do_nothing": "fail"},
  "log": [{"by": "agent", "call": "place", "args": {...}, "result": "..."}]
}

4 · Scene API (layer 1)

FunctionDoesReturns
list_scene()base and added objects with kind, size, pose, locked flag; free table areaJSON
list_assets(query)pack assets and articulated objects matching a word (§7)names, sizes, licence
add_object(source, size, colour)source = primitive:box|cylinder|sphere, a pack asset, a LIBERO articulated object; later objgen:<id>new object id (not placed yet)
fits(obj, target, relation)geometry with clearance: inside / on / next to; graspable (≤ the 2F-85's 85 mm opening)yes/no + the limiting dimension
place(obj, relation, target, allow_resize)does the search itself: samples poses in the target's free space, settles physics, and if allowed tries smaller sizes within the kind's boundsplaced (+ any resize) or infeasible with the reason
resize(obj, scale)added objects only, within bounds (§5)new size or refusal
set_task(instruction, success)task text + a success rule from a fixed set (inside, on, stacked, ordered stack, out of)ok or why the rule doesn't fit the scene
check()settle; overlaps; reachable; inside the area the real cameras saw; scripted expert; do-nothing policyper-check pass/fail + reasons
render(view) / save()exterior / wrist / free view images; write the configimage paths; config path

The search lives in the tools, not in the model: a small local model is weak at multi-step search, so place(..., allow_resize=True) returns one clear answer, e.g. "placed; block scaled 4.0 → 3.0 cm" or "infeasible: drawer interior height 2.5 cm < smallest block 3.0 cm".

5 · Rules the API enforces

  1. The base scene is locked. Reconstructed objects, table, cameras and robot are never moved, resized or removed by the agent. (Perturbing base objects is a separate, user-driven feature.)
  2. Only added objects can be resized, and only within bounds for their kind (first proposal: block 2–6 cm, cup 6–10 cm tall, bowl 10–20 cm across, fruit 5–9 cm) and still graspable when the task needs a grasp. Every resize is logged with its reason and reported to the user.
  3. Infeasible is an answer. When nothing within bounds fits, the API says why and the agent reports options (another container asset, a smaller object kind), never a silent change.
  4. Everything goes through the config, rebuilt and recompiled with MuJoCo's model-editing API. Never patch the compiled .mjb: on 10-23 that left stale collision bounds and a block sank 0.4 cm unnoticed.
  5. Added objects stay inside the area the real cameras saw (wrist table texture exists there; checklist C3), on the table, reachable by the arm.
  6. A task enters the eval set only after check() passes and the user approves in the inspector.

6 · The agent (local, Ollama)

User, 10-28: "we will have a separate agent most prolly local ollama inference for that".

  • Model: an ~8B model with tool calling in 4-bit (e.g. a Qwen3 8B); fits the 8 GB card, but not next to a policy run, so it goes through prim's GPU gate like any GPU job. CPU-only inference works but is slow.
  • Tools: the layer-1 functions, ~6–8 of them, strict schemas; every input validated on our side with error messages the model can act on (small models make more malformed calls).
  • Loop: prompt → tool calls → results → final report (what was added, resized, placed; the task; check results; anything infeasible). The user reviews in the inspector.
  • Programmatic tool calling (model-written scripts that call the tools) is a Claude API feature, not available here; the search inside place replaces it.

8 · Checks on every result

From REAL2SIM_CHECKLIST_V1.html: B1 settle, B2 collision shapes, B3 the scripted expert solves it (a new expert per task type is expected; user 10-26), D3 every object visible, D5 contacts look right, E2 a do-nothing policy doesn't succeed, E4 the success rule fits the task type, C3 inside the camera-covered area. Added objects have no real reference, so the image-vs-real checks (C1, D1) don't apply to them.

Demo prompts (acceptance): (1) "put a red block in the middle drawer" → added drawer, block placed inside, resized only if needed and reported; (2) "add two cups next to the bowl" → placed, settled, reachable; (3) an infeasible one, e.g. "put the bowl in the drawer" → the bowl is a locked base object and too wide: refused with the reason.
