3.1 What we already know

  • No public dataset labels the decision point; they all mark where the failure shows (res21, 10-12). FailTime has human onset labels with 50 ms agreement (CC-BY-4.0); we adopt its onset rules.   • The spec's labels come from outside the model (D16): actions, telemetry, sim state, VLM. So labelling is black-box by design.
  • Where humans are needed, given §2: in sim, the triage service finds divergence and decision point automatically by branching. On real-robot logs there are no snapshots to branch from, so onset, phase, mode and the likely root have to be labelled from video and telemetry. That is where human labelling is unavoidable.
brain: what are the labels for? A real-log triage, B training data for monitors and judges, C audit and QA of automatic labels. Recommended A with C built in.
User: this is essentially our mining spec design, or am I missing something?
brain: not missing anything. It is the mining spec filled by humans instead of rules: D1 (one instance, three uses), D16 (labels from outside the model), D15 (exact / estimated / unavailable sources, which real logs need), FailTime onset rules already adopted. 3.2 Humans adjudicate some, then VLM + telemetry takes over: is that E7?

User: so humans adjudicate some of it, then VLM + telemetry takes over? That's essentially what we are testing in E7, right?

Answers are scored against sim truth (_gt_scene_object_pos, fingerpad distances), not human labels. The design is a three-way check: instruction = intent, telemetry = mechanics, VLM = which object / where.
  • Status: not shown yet. Nemotron hallucinates; Cosmos-Reason2-2B answers almost the same every time; the approach-truth rule was corrected (rim grasps); the NIM controls pass was paused at 84/148 on 10-12. No scored result.
  • What E7 does not test, but the product needs:

    2. The handoff rule. Which items the VLM keeps and which go to a human: per-question-type accuracy thresholds, plus routing every case where instruction, telemetry and VLM disagree.
    3. How many human labels are needed before the VLM's accuracy on a customer's data is known well enough to switch over.
  • A possible real-video test without a robot cell: FailTime has human onset labels on real ALOHA / SO-101 video (CC-BY-4.0). Scoring VLM + telemetry against those humans would be the real-video half of E7. Whether FailTime ships the telemetry needed is unchecked.
  • As a product it is iMerit's usual model: human-calibrated, model-scaled labelling. What's ours is the telemetry-gated closed questions, which make VLM answers checkable, and the three-way disagreement flag that decides what humans see.

3.3 Is the VLM incompetent, or is it our input? Combining both views

User: is the model incompetent? Or can we combine both images, or combine features from them? When I was adjudicating, I looked at both images to get an idea of what was going on.
brain: E7 already shows both views, but in the crudest way, so "incompetent model" vs "bad input" hasn't been separated yet.
  • What E7 sends now (e7_render.py line 192, e7_vlm.py header): one still per event, agent view and wrist view concatenated side by side into a single image, rotated 180° as the policy saw it. The prompt does say which half is which ("Left half … third-person camera. Right half … wrist", vlm_label.py CLOSED_PROMPT; corrected by prim 10-14). What's missing is separate images, any guidance on combining the two views, and motion: a single frame, except in the bisection mode.
  • Input problems that could explain the failures, independently of the model: (1) upside-down images, which VLMs are trained on far less; (2) one merged image: the halves are named in the prompt, but the model gets no separate images and no guidance on combining the views; (3) no motion: a human sees the gripper closing and the object rising across frames, but a still can't show "holding" vs "touching"; (4) small images at --scale 0.5; (5) small models (Cosmos 2B).
  • Cheap way to separate model from input: an input-format ablation on the same questions and the same truth, changing one thing at a time: unrotated; two separate labelled images ("front camera", "wrist camera"); a frame before plus the event frame (motion); full resolution; telemetry facts in the prompt ("gripper closed at t=31; object z +3 cm"). If accuracy jumps on one change, it was the input. If it stays flat across all of them, it is the model. API calls and CPU only; no GPU.
  • Combining features instead of pixels: encode both views with a frozen image encoder (SigLIP / DINOv2), concatenate the two embeddings (plus telemetry), and train a small classifier on the human-adjudicated items. That is literally "humans adjudicate some, then the model takes over": few-shot learning from human labels, compared with the zero-shot VLM. It also gives a confidence score for the handoff rule (3.2, gap 2).
  • Caveats: the E7 code is impl's, in the worktree; any change goes through the user, then prim, then impl. The handreview labels exist (runs/root_signals/e7/handreview/), but how many items they cover hasn't been checked.

3.4 Merging tokens from both views (a DiT-like fusion): does our VLA correlate them?

User: is there a way to get better accuracy by merging tokens from the two views, a DiT kind of approach, so there is at least some correlation between agent and wrist view? In our VLA, do both views get correlated or not?
brain: yes, GR00T N1.7 correlates the two views, in three places (read from third_party/lerobot/src/lerobot/policies/groot/groot_n1_7.py and action_head/cross_attention_dit.py):
  1. Backbone (Qwen3-VL, cut at layer 16): both camera images become image tokens in one sequence with the instruction, and the language model's self-attention mixes them. Its attention is causal and the agent view is the first image block (R-060 G0a), so the wrist tokens can attend to the agent tokens but not the other way round. This follows from the standard causal LM mask; not checked for a custom mask.
  2. vl_self_attention: a small transformer over all vision-language tokens before the action head (use_vlln, vl_self_attention_cfg), so the views mix again.
  3. Action head (AlternateVLDiT): the DiT cross-attends to the image tokens of both views together on alternate blocks and to the text tokens on the others.
The views still keep separable token positions: R-042 could splice the wrist tokens alone and found they carry start pose (W = 0.88).
  • The same holds for our VLM labellers. Any multi-image VLM puts both images' tokens in one sequence and attends across them. So the first, cheap fix is to send two separate, labelled, unrotated images instead of one stitched upside-down image (the ablation in 3.3). That gives the "merging" for free, inside a model built for it.
  • If that isn't enough, a small fusion model, DiT-style: frozen encoder tokens from both views (DINOv2 / SigLIP), plus telemetry tokens, plus a few learned query tokens that cross-attend over all of them (Perceiver / Q-Former style), with one classification head per closed question. In sim, sim truth provides unlimited free training labels, so no human labels are needed to train it. Humans are needed only to check and calibrate it on real video.
  • Why not use GR00T's own fused features? They already merge both views with the instruction, from exactly these cameras, so a probe on them would probably be accurate. But that breaks D16 (labels from outside the model) and inherits the policy's own misperceptions (UQ6 circularity), and it needs weights, so it isn't black-box. It is fine as an internal comparison, not as the product's labeller.
  • New evidence (prim, 10-14; preliminary, unchecked): the user labelled the 40-item E7 hand-review set. On the 26 items the user decided, the user agrees with sim truth on 15. For "held" and "on plate", a single frame is ambiguous even for a human. Cosmos-2B agrees with the user on 10/26. So part of the problem is the single still, not only the model, which supports adding motion (two time points or a short clip) first. A full report awaits a new session.
  • Suggested order: (1) the input ablation (separate, labelled, unrotated, two time points); (2) only if accuracy stays low, the fusion model trained on sim truth; (3) optionally a GR00T-feature probe as an upper-bound comparison.

2.2 The user's two ideas

User: (1) If the corrector works, the episode is no longer a failure. The original run failed, but with our mechanism it succeeds: that rescue could be the offering, so measure success rate with the corrector. (2) The user's own aim was to simulate a rollout from that point for retraining: can the corrector also judge the root?
brain on (1), a rescue layer as the offering:
  • The metric is paired flips: failures turned into successes, against successes turned into failures, on the same seeds (McNemar), plus a no-harm check on nominal runs.
  • The controls decide whether it is worth selling. The paper's own Table 4 shows a fixed shorter horizon recovers most of the gain (H = 10: 64.5% vs H = 50: 48.7%), and truncation alone gives 60.35 of the 64.35. A product claim needs to beat (a) a fixed shorter horizon and (b) a random trigger at the same number of replans. Otherwise the "mechanism" is a knob the customer can set themselves.
  • Where it can and can't rescue: not start pose (decided at forward 0; the monitor can't fire before ~step 25; and a plain re-run flipped 0/22 in R-053). Plausible for mid-episode failures: scene 1327 regrasp, objects moved mid-task (the paper's largest real gain, +28 pp).
  • Black-box fit: needs control over execution (interrupt a chunk and ask for a new one), plus the vision-encoder swap from 2.1. No weights.
  • Already in the repo: the 6-arm first-chunk test (c9d) and the "interrupt-and-replan framework" assessment in PAPERS_WORKING_NOTES (not novel as a method; valuable as a test bed for triggers with the controls the paper lacks).
brain on (2), the corrector as a root finder:
  • Firing time is a candidate, not the root. The monitor fires when the world diverges from what the action predicted. That is the onset of a symptom. res21's 10-12 verdict: onset ≠ decision point, and the decision point can only be measured by intervening.
  • Replanning is that intervention. Restore the sim state at step t and replan from there. If replanning at t rescues the episode, it was still recoverable at t, so the root is later. If replanning at t fails but at an earlier t′ succeeds, the root lies between t′ and t. A short bracket search (starting at the firing time, stepping back) gives a black-box root estimate. It is our correct-at-forward-k method (R-044, R-057), with "replan" in place of "execute the nominal chunk", so no oracle episode is needed.
  • It feeds the retraining offering directly. The bracket gives the root state, which is the input ROOT_TO_GOAL S1 needs. The rescued replan itself is a candidate corrective rollout from that point. Caution: Mulligan found that training on the policy's own successes hurt (−3.4 pp), so DMP-retargeted human demos (ROOT_TO_GOAL) are the safer source and the policy's rescues need a separate arm.
  • Risks: E3 (action-level) fired after every grasp, failed or not, so false triggers may be common. "Smooth and wrong" failures may not trip a prediction-error monitor until late. Stochastic replans may not differ enough to rescue anything (R-053's 0/22 on start pose). The image-latent version has never been run on our data.

2.3 First divergence vs decision point, and how this fits the mechanism layer

User: can't we find both the decision point and the first divergence in the same run? And our mechanism work already maps each failure to a mechanism; how do the two fit?
brain:
  • From one passive run, only the first divergence. The decision point is counterfactual ("would a different action from here have saved it?"), so it needs at least one branch. In sim the branches can come from the same episode: snapshot the state as it runs, then branch from earlier snapshots. A bisection over 18 forwards is about 4–5 branch points, × a few seeds because the policy is stochastic. Inside a live corrected run there is one free bit: if the replan at the firing time rescues it, the decision point was after the divergence; if not, it was before, and back-stepping is needed. On a real robot without snapshots, only the divergence is available.
  • What the spec already says. root is defined as the first divergence (D13), labelled from outside signals only (D16). mechanism is an optional block (D7) for why (which input channel carries the fault, found by white-box splices) and is validated only on perturbations. The decision point has no field of its own today.
  • Where the decision point comes from now. R-044 / R-057 correct-at-forward-k. It needs a recorded nominal twin episode (an oracle), so it exists only for perturbation-induced failures, and it sits on the mechanism side. So "the mechanism work already does that" is right, but only where a nominal twin exists.

2.6 How the black-box corrector monitor runs, and is it promising?

User (10-14): how will it work at run time? We own the vision encoder and they provide rollouts? Is it promising?
runtime: how it runs. They provide demos (to train the predictor) and some successful rollouts (to set the threshold); at run time, only camera frames and executed actions. Their weights are never touched.
  • Setup (once per task, offline). (1) Run our own frozen, off-the-shelf vision encoder on every demo image to get scene features z. (2) Train the ~40M predictor: input the scene now (zt) plus the next 10 actions, output the expected feature change zt+10 − zt ("if the robot does these 10 actions from here, the scene should change like this"). (3) Set the alarm threshold conformally on their policy's successful rollouts (e.g. at most 5% of good runs ever alarm). The paper has no such calibration; we add it.
  • Each control step (a sidecar next to their policy). Encode the current image → zt; compare the change predicted 10 steps ago with the change that actually happened; score = 1 − cos(predicted, actual). Above the threshold → call their interrupt: the policy drops the rest of its 16-action chunk and replans from the current image (that replan is where VLA-Corrector's gain comes from). Nothing is fed into the policy; we only decide when it is re-queried.
  • Limits. It judges an action only 10 steps later, and the released code can't fire before ~step 25, so it is no use for start-pose failures. Without an interrupt call in their API it can only alarm. Per-step cost is one image through our encoder plus a tiny MLP, probably tens of ms on a GPU (not measured). A generic encoder isn't tuned to their scene, and whether the predictor still works is untested. The action-level version (E3) fired after every grasp.
  • In the v0 triage service it doesn't run on their robot: we run their policy through the API in our sim with the monitor watching; its firing step is the first divergence, and we snapshot and branch there (policy replan vs DMP good action) to classify timing / competence / unrecoverable.   • For. (a) Its best real-robot result is "object moved mid-task" (+28 pp), and LIBERO-MAX's largest GR00T loss is the same kind of event, target relocation (−52.5). (b) Almost all of its gain comes from truncation, which needs only the interrupt call, so the black-box version keeps nearly everything. Gradient guidance (OGG) needs weights and is lost, but it added ~4 pts, within noise, and was negative on Hard. (c) LIBERO-MAX fires its events at a known moment (pre_grasp_proximity), so the true onset is known. "Does the monitor fire shortly after the event, and rarely otherwise?" is a cheap, clean first test that no other data set here gives us.
  • Against. (a) Its own Table 4: a fixed H = 10 gets 64.5 vs 48.7 at H = 50, so a customer can get most of the rescue by turning a knob. LIBERO-MAX's GR00T setup already uses 8 steps per forward, which leaves less to gain. (b) There is no false-alarm control as published, and E3 suggests contact events will trip it. (c) A generic encoder instead of the policy's own features has never been tested. (d) The detector field is crowded (12+ papers in 2026).
  • The test that decides it (proposal only, nothing approved; runs after LIBERO-MAX reproduces). On Dynamic episodes: monitor-triggered replan vs fixed shorter horizon vs random trigger at the same number of replans vs an oracle replan at the known event time, scored by paired flips plus a no-harm check on Base.
