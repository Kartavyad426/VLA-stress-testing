Verdict: separate on diagnosis, overlapping on the data primitive
  • What FLARE is. A data-and-orchestration recipe on π0.5 in RoboMimic, with two parts.
    • Retry (in-distribution errors) injects random pose excursions plus interpolated "bridge" segments into every demo: at the start and between subtasks. The policy thereby learns the next correct action from many arm poses.
    • Reset (out-of-distribution errors) has Gemini-2.5-Pro read failure videos and name the object to reset and the failure time. Humans then record 20 reset demos per object from the reconstructed failure state, and a separate LoRA adapter is trained per reset skill. At run time, Gemini watches and swaps adapters.
  • How it diagnoses. Semantically, not mechanistically. The claim that VLAs "associate task progress with the joint configuration" is argued from the data regime and never tested: no input ablation, no probe, no intervention. Failure analysis is an MLLM classifying videos, at 66–96% accuracy on 50 hand-labelled videos.
  • Numbers. On 9 RoboMimic tasks, π0.5 72.2% → FLARE 84.0% (325/450 → 378/450, p ≈ 3×10⁻⁵) verified. In the 4-task ablation, bridging alone moves 121 → 140 of 200 (p = 0.06). Adding resets moves 140 → 147 (p = 0.51, not distinguishable). Reset skills for the harder object succeed 20–24%. Real robot: 62.5 → 75% and 45 → 55% at 40 trials (both p > 0.3).
  • Not tested: start-pose perturbation. The bridge at trajectory start (dinit) exists "to decouple the very first action from a fixed starting pose". But the evaluation uses standard RoboMimic initialisation and never perturbs the robot's start or measures recovery from an injected pose error.
  • Bridging vs our Option A. They are the same primitive: drive from an off-distribution arm pose to a valid point on a demo, label it, and continue. Option A is narrower but more specified on four points:
    • the start distribution (the real eval perturbation, stratified by cm);
    • a closed-loop privileged controller instead of open-loop linear/SLERP interpolation;
    • a join point at the earliest reachable approach waypoint;
    • explicit dose accounting and a no-training rescue check before any training.
    FLARE adds mid-trajectory bridges and per-skill adapters, both worth borrowing (§8).

1. The claim, and what it would take to prove it

FLARE's central argument verified:

  1. Demonstrations are trajectory-monotonic: the arm follows a narrow manifold of poses correlated with task progress.
  2. So the policy learns to read progress from its own configuration sr instead of from the environment se.
  3. So a valid-but-unusual pose (an "ID error") is misread, and the policy fails to retry.
  4. Injecting pose excursions and bridges breaks the coupling.

A proof of step 2 would need an intervention that changes sr at fixed se: put the arm at a "placing" pose with the cup ungrasped, and show the policy acts as if placing. Step 4 needs a test that injects pose errors at run time and measures recovery, with and without bridging. The paper does neither. Its evidence is end-task success on the standard benchmark, where ID errors arise only naturally and are never counted.

The Reset claim is that MLLM-guided reset skills recover OOD failures. It needs the reset contribution separated from bridging; Table 3 does that, and the gap is inside noise (§5).

2. Formalism

2.1 State split and error taxonomy verified

The world state is split into environment and robot: st = (set, srt). The observation is a render of the whole state. The policy is Markovian over chunks: at ∈ 𝒜K ~ πθ(· | ot, I). Let 𝒮etask be the environment states on any successful path.

ID error:  set ∈ 𝒮etask  and  P(srt | set, 𝒟demo) low  → Retry(1)
OOD error:  set ∉ 𝒮etask  (e.g. toppled cup)  → Reset skill πreset,j moves se back into 𝒮etask(2)

On our map: a LIBERO-Plus robot-initial-state perturbation is a pure ID error at t = 0. The scene is valid; only sr0 is off the demo distribution. Scene 1327's R-056 failure, grasping too high and then regrasping 5–7 times, is a chain of ID errors ours.

2.2 Perturbation & bridging verified

Start from a MimicGen-composed trajectory of subtask segments Ttask = (a0, …, aN). Insert a two-phase segment before the first segment and at every subtask junction:

Taug = (dinit, a0, d0, a1, d1, …, aN),    di = ( dAi perturbation, dBi bridge )(3)
  • Perturbation dA: random joint velocities or end-effector motion to an "arbitrary" pose. The bounds in the main experiments are rotation ≤ 45° and translation ≤ 0.5 m.
  • Bridge dB: planner-free kinematic interpolation from the perturbed pose (p0, q0) to the start pose of the next segment (p1, q1). Position is interpolated linearly and orientation by SLERP, over u ∈ [0, 1]:
p(u) = (1−u) p0 + u p1,    q(u) = [ sin((1−u)Ω) q0 + sin(uΩ) q1 ] / sin Ω,   cos Ω = ⟨q0, q1⟩(4)

Training set construction. Perturbation actions are never used as targets. For each augmented trajectory, the training set gets:

𝒟task aug ⊇ { (ai, ai+1, …) } ∪ { (dBi, ai+1, ai+2, …) }(5)

The intended effect is to widen the support of P(sr | se, 𝒟), so that every environment stage is seen from many arm poses. The bridge labels are what teach the state-conditional "go back to the work from here".

Unspecified details inferred:

  • how many interpolation steps a bridge takes, and at what speed;
  • whether bridges are executed in sim and filtered by task success (a "data generation success rate" is reported, so some filter exists), or kept open-loop ("the benefit … far outweighs the noise from rare, invalid trajectories");
  • the sampling share of bridge subsequences vs original ones;
  • whether π0.5 receives proprioceptive state. Their formulation conditions on ot and I only.

2.3 Reset: MLLM failure mining verified

  1. Run the retry-capable policy for "hundreds of episodes"; keep the videos and the simulator logs.
  2. Gemini-2.5-Pro (temperature 0.7) reads each failure video and returns JSON with:
    • failure_reason;
    • recovery_strategy (retry / reset);
    • reset_object, chosen by an "operation-dependency" rule: reset the first object that must be manipulated, e.g. open the lid before the stuck pod;
    • error_group (the objects jointly forming the error);
    • failure_timestep.
    The full prompt is in supplementary Table 6.
  3. Use the timestamp to pull the exact MuJoCo state. Treat the error group as a rigid "semantic failure asset" and re-place it in new scenes, preserving relative poses.
  4. Collect 20 human demos per reset skill from those states, then augment to 500 with the same perturbation & bridging.

2.4 Training and orchestration verified

  • Base: π0.5.
  • Trainable: LoRA on the language model and action expert; "all other model parameters remain frozen", "following the official training practices of π0.5". Adam, constant LR 2.5×10⁻⁴, no decay. Steps and batch are not given.
  • Adapter library: one task adapter trained on 𝒟task aug, plus one adapter per reset skill trained only on its own data (prompt "reset the cup").
  • Run time: the task adapter executes. An online Gemini monitor watches. ID errors need no action. On an OOD error it swaps to πreset,j, confirms the reset, then swaps back.
  • Data: 10 human demos per task → 500 via MimicGen, then P&B. Reset: 20 → 500. Real robot (Piper arm, top and wrist RealSense): 10 → 50 per task or skill, with Any6D object poses in place of simulator state.
A cross-check from our π0.5 reading

In openpi's pi0_config.py, the LoRA freeze filter freezes only parameters under llm. SigLIP and the action projections stay fully trainable. See SPATIAL_ADAPT_MATHS.html §5.1, verified against the source. If FLARE used openpi's stock LoRA config, as "official training practices" suggests, its "LoRA" also full-fine-tunes the 400M vision tower, despite the text saying everything else is frozen inferred. This matters only for comparing trainable sets: FLARE vs our LoRA head (vision frozen).

The MLLM decides which objects need reset skills and which states to start reset demos from. That is targeting at the level of failure type, not mechanism. For retry, nothing is targeted: P&B is applied uniformly to all demos at every junction.

6. Critique

  • The causal story is asserted, not shown. "The robot's pose might be at a placing position, causing the policy to infer the task is at the placing stage" is a hypothesis. A fixed-se, varied-sr intervention, which is exactly a splice, would test it cheaply in simulation. The paper never runs one.
  • Recovery is never measured directly. No injected-perturbation benchmark, no count of retries, no ID-vs-OOD failure rates before and after. The 12-point gain could come from bridging teaching recovery, or from bridging acting as pose-diversity augmentation for ordinary execution. Those are different mechanisms with different implications.
  • No equal-data control. FLARE sees more training sequences than π0.5. A "π0.5 + matched extra MimicGen demos" arm or a DART-noise arm at equal count is missing.
  • The reset half is statistically invisible (§5.2), and its weakest skills are near-useless (20–24%). The MLLM's timestamp accuracy (66–78%) bounds how precise the mined reset states can be.
  • The open-loop bridge quality is unknown. Linear plus SLERP interpolation ignores obstacles and joint limits. The admitted "rare, invalid trajectories" are kept as noise.
  • Choice of start-pose perturbation is unexamined. dinit exists for this purpose, but robustness to start pose is never evaluated. This is precisely our setting, so FLARE gives no evidence for or against bridging fixing start-pose failures.

8. What it means for our stack

8.1 Verdict

Separate on diagnosis, overlapping on data generation. FLARE has nothing resembling our attribution: no splices, no transfer fraction, no time localisation, no rescue, no mechanism readout. Its "targeting" is a semantic failure taxonomy from an MLLM plus uniform augmentation. Our Q4 novelty statement survives. The data primitive, bridging to decouple arm pose from task progress, is shared and published, so Option A should be framed as "FLARE/MimicGen-style bridging, specified by the mechanism", not as new.

8.2 What to borrow

B1 · Junction bridges for the grasp, aimed at scene 1327

R-056's regression is a grasp closing 5.5–5.8 cm high followed by 5–7 regrasps. That is an ID-error loop at the grasp junction, and 16 of 100 minted demos carried a failed first grasp. A FLARE-style excursion + bridge at the pre-grasp junction teaches "re-approach from here" with clean labels. Include it in Option A as an optional second insertion point, with its own dose line.

B2 · Run the magnitude sweep as a pre-registered arm

Their yield-vs-success trade-off has the same shape as ours: minting yield fell 0.9 → 0.2 with offset. Pre-register Option A's generator yield per offset band (already a CPU gate) and a training-side sweep: max offset 12 / 16 / 20 cm at matched episode count.

B3 · Per-skill adapters to protect nominal behaviour

FLARE keeps one LoRA per skill to avoid interference. Our 1327 regression was a nominal-task regression caused by start-pose training. Options: a separate "bridge" adapter used only for the first k forwards, then handed back to the base, or WiSE interpolation (already queued under D19). Either is the training-time version of our rescue's drive-then-handback.

B4 · Failure assets for reset-like states

Their "semantic failure asset" re-places a failure configuration rigidly in new scenes. That is a cheap way to multiply our rare failure states, such as the knocked-bowl or premature-close states, into training starts. In sim we have exact states, so we don't need the MLLM step.

B5 · Don't rely on an MLLM for frame-level targeting

66–78% timestamp accuracy is too coarse for a forward-level specification. Our privileged simulator signals and the splice already localise to a forward. MLLM triage (we have vlm_label.py) is useful for type, not time.

B6 · A test FLARE should have run, and we can

Run a fixed-se, varied-sr splice on GR00T mid-episode: arm displaced, bowl ungrasped. Does the action follow the arm or the bowl? It answers FLARE's untested "pose reads as progress" hypothesis on our model with machinery we already have (the R-039 arms). That is a publishable addition: a mechanism test of the assumption behind bridging-style augmentation.
