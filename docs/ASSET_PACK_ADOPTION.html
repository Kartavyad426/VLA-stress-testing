5 · Stage 3: redundancies

Three kinds found; how to deal with them is the user's decision (§7).

  1. Exact duplicates across libraries: 8 LIBERO scanned models = GSO models (§4a). Same mesh, different collision (LIBERO hand-made boxes vs GSO V-HACD).
  2. Category overlap: up to 276 of 416 LIBERO-Plus categories have a Kitchen-MJCF or GSO counterpart (§4b). LIBERO-Plus is research-only, so for a product the CC BY copy wins; for research the LIBERO-Plus copy can stay under --assets libero.
  3. Variants inside a pack: Kitchen-MJCF has 6–25 models per category (922 total); GSO has some near-duplicate product entries (e.g. Granimals_20_Wooden_ABC_Blocks_Wagon three times with id suffixes). Retrieval needs either all variants (more choice) or one per category (faster index).

5a · Making the packs retrievable: build_scene hook (prototype)

Before: the packs were on disk but not retrievable: --assets accepted only libero|none, the name match could not read GSO product names or Kitchen's two-level folders, the bowl was hard-coded to LIBERO's akita file, and GSO's XML sets no mass (MuJoCo's default gives a ~10 kg bowl) [V].

What was built (user go, 10-19 "start on that"):

  • 10-19 version, kept as history. Superseded on 10-20: cc removed, YCB added, redaction instead of ellipsoids, committed 643c5c1 (§7a).
  • experiments/asset_pack/catalogue.py (new, mine): pack catalogues (kitchen 922 models, gso 1,030, cc both = 1,952), a name match, a size check, mass/friction setup that keeps each pack's collision parts, and the property layers below.
  • experiments/asset_pack/build_scene_assetpack.diff: the proposed change to res31's build_scene.py (not applied; sent via prim). New --assets kitchen|gso|cc and --object_props; libero and none unchanged.

How a pack object is built

  • Match: head noun of the detected label against Kitchen categories / GSO name words; candidates sharing the label's other words (e.g. "black") first. Weak by design until stage 4: "apple" name-matches a card game box.
  • Size check: both packs are metric, so a candidate needing a rescale outside 0.5–2× is the wrong object and is skipped. That is what rejects the card game for the apple.
  • Bowl: retrieved from the pack and scaled to the fitted rim; it keeps kind="bowl" so replay, make_tasks and scene_checks still find it.
  • Collision: the pack's own convex parts are kept (cavity stays open); visual and Kitchen "region" geoms are made massless.
  • Mass/friction/scale: label override > category:<noun> override > category default (empty until sourced) > default. Default = density 500 kg/m³ × the visual mesh's convex-hull volume (build_scene's existing density for retrieved meshes), friction [0.95, 0.3, 0.1]. Every object's values and their source layer are written into scene_fit.json.
  • No plausible mesh (apple, radish; user decision 4a): fitted ellipsoid, with its footprint from the mask width (lesson 14) instead of the point spread, which made the c3 radish 0.38 m long.

What the expert numbers mean

  • Bowl tasks are equal or better. c3 "put the … block in the bowl": 24/25 in both. orange: all bowl tasks equal except "move the yellow block next to the bowl" 0/5 → 4/5.
  • That gain is mass, not shape. In both versions the expert bumps the bowl during that task; in variant 0 it moved ~9.6 cm (0.098 kg LIBERO bowl) vs ~6.8 cm (0.55 kg GSO bowl), so the heavier bowl stays within the 8 cm "next to" gap more often. Not evidence the asset is better.
  • The c3 loss is entirely the apple and radish ellipsoids (decision 4a): apple 5/5 → 0/5, "next to the radish" 4/5 → 0/5, "next to the apple" 5/5 → 4/5; radish was 0/5 already. The apple ellipsoid is 14.4 cm tall (height from the point spread), where the LIBERO mesh was 5.1 cm. Blocks-only tasks are within ±1.
  • Mass default is a real choice: "density 500 × hull volume" makes the bowls 5–6× heavier than the LIBERO bowl at the same scale. Neither number is sourced from a real bowl.

A first cc run on c3 scored 10/65: only variant 0 of each task ran, because the 0.38 m radish ellipsoid left no overlap-free layout for make_tasks' randomiser. Fixed by the mask-width footprint above; --assets none has the same defect (not changed; for res31). Early runs used EGL (GPU) rendering for build/replay before I switched everything to osmesa (CPU). YCB (stage 1 again, 10-20)

  • Licence: CC BY 4.0 per the AWS Open Data registry entry, which links the official site (the official site itself returned HTTP 500 when checked) [V]. Habitat's YCB copy states the same.
  • Source: official google_16k meshes (obj + png) from the ycb-benchmarks S3 bucket; 85 archives, 603 MB; each checked against its listed size and md5 (ETag). 076_timer's archive is 45 bytes upstream (empty), so 84 objects. On disk: data/real2sim/asset_packs/ycb/src/ (922 MB unpacked, gitignored) [M].
  • No MJCF ships: the temp catalogue.py writes one per model to ycb/mjcf/ (visual mesh + the same mesh as one convex-hull collider). Hull collision fills cavities, so YCB containers (bowl, mug, cups, pitcher) are not offered for the bowl.
  • Apple: 013_apple is 7.2 × 7.5 × 7.5 cm; the c3 apple's mask width is 5.9 cm, so scale ≈ 0.8, inside the 0.5–2× check [M]. No radish in YCB.
