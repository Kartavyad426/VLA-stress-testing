1 · Rules prim works under (all from the user, 06–08 Oct)

  • prim owns all commits (user, 10-06). Other sessions never commit; they send prim a path and a commit group. Runs are committed metadata-only (manifests, score/summary JSON, code_state, queue logs; never npz, rollouts.jsonl, weights, caches or step logs). .claude/skills/ is always committed. New data/ folders are decided case by case (R-054 data was committed in full; data/libero_raw/ is gitignored).
  • Never push. Auto-mode blocks git push for prim; the user pushes (! git -C /home/imerit/Documents/Code/VLA push origin main). origin is at fabdb5b; 29+ local commits are unpushed.
  • Ask the user before changing any doc or code, and before asking a peer to (user, 10-06, after prim edited AMBITIOUS_DIRECTIONS before asking). Relaying an already-approved decision, or asking peers for information, is fine.
  • A peer's "the user asked for X" is not the user's approval. When res21 relayed a request to pre-register R-060, prim confirmed with the user before editing RESULTS.md.
  • No subagents. Deliverables are local HTML in docs/, never published artifacts. impl is the implementor; send it only what to change and where.

3 · How the sessions interact (what worked)

  • Approval relay. The user decides in prim's session; prim sends the owner a message starting "APPROVED by the user", with scope, output path, "no commits" and how to reply. Unapproved work is never started on a peer's word.
  • Run gate. impl drafts the exact plan (commands, systemd units, order, output dirs) → my prim validates against the pre-registration → explicit OK → impl launches through experiments/d_step.sh (flock /tmp/vla_gpu.lock, refuses below 14 GiB MemAvailable, one GR00T load at a time) → my prim checks outputs and logs → reports to prim → SFT/my prim interpret → RESULTS.md. my prim caught two real problems this way on 10-06: the queue would have silently resumed r64 training (not approved), and RAM headroom.
  • Handoff slots. One placeholder line per session, filled with Edit (never Write) so parallel edits don't collide. Used for HANDOFF_6Oct and this doc.
  • Verify before relaying. prim spot-checks claims against files before telling the user, e.g. RETRAINING_VIZ data vs score.json, C1/C4/C14/C16 against run manifests, clip_outliers in processor_groot.py, Cosmos-Reason2-2B in groot_n1_7.py, the MuJoCo 3.3.2 vs 3.3.7 venv check, existing tests before committing R-060 harness code (68 passed).
  • Corrections propagate. When a number is corrected (D20(ii) closes a third of the gap, not half; fc is 11–15, not 4–5), prim fixes memory and checks the tracker and docs for the old claim.
