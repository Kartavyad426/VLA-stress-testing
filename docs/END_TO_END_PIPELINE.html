0 · The picture

We run a robot policy in simulation, collect the episodes where it fails, and work out where each failure began (the root) and why (the mechanism). Where the mechanism calls for new data, we generate a corrected demonstration from that point. We then retrain and re-test on episodes the training never saw. The loop then repeats with the new policy.

The loop is not built end to end. Diagram (b) colours each step by how far it has got.

1 · Glossary

VLA (vision-language-action model)
A robot policy that takes camera images, a text instruction and the robot's joint state, and outputs robot actions. Most are built on a pretrained vision-language model.
GR00T N1.7
NVIDIA's open VLA, and the policy in all our experiments. We run its LIBERO-Spatial fine-tune (nvidia/gr00t17-lerobot-libero_spatial-640). Each call predicts a 40-step action chunk. Our harness executes 16 steps of it and then calls the model again. LIBERO-MAX's protocol executes 8.
LIBERO
A simulated tabletop benchmark (MuJoCo physics via robosuite, a Franka Panda arm). Tasks are written in BDDL files (§2). It has four suites: Spatial, Object, Goal and LIBERO-10. Each task comes with 50 human demonstrations. We mostly use LIBERO-Spatial: 10 tasks, each "pick up a black bowl and place it on the plate", in different layouts.
LIBERO-Plus
LIBERO tasks with controlled perturbations: camera pose, robot start pose, lighting, texture, layout, language and sensor noise. It also ships a 1,125-object model library.
LIBERO-MAX
A paired benchmark built from LIBERO-Plus and LIBERO-PRO variants. Each case has a Base episode and a Dynamic episode. The two are identical until the gripper comes within 0.18 m of a named object. Then one event fires in the Dynamic episode: the target is moved, the camera shifts, sensor noise starts, and so on (8 event types). The "Lite" set has 800 pairs. Because the event step is known, it is a clean test bed for "where did it go wrong".
Rollout
One episode of the policy acting in simulation, from a start state until the success check fires or the time limit runs out. We log the state and action at every step.
Task
Starting scene + instruction + automatic success check + time limit. See §2.
Root
The step at which we say a failure began. There are two rules, and we keep both because they can disagree on the same episode (§5): first failure, the first failure event in time; and first unrecovered failure, the first failure event that the policy never made good later in the episode.
Mining instance
A structured JSON record of one failure, defined by our "mining spec". It holds the task, the root event, the situation at the root as numeric fields with tolerances, the success test for that phase, and the evidence. It is the input for finding or producing data that fixes that situation.
Mechanism
Why the failure happened, stated so that it picks a fix. Here: which input carries the failure into the action (which camera, image vs state) and at which model call the outcome is decided. Example: a specific input channel (e.g. the wrist camera).
DMP (dynamic movement primitive)
A way to encode a demonstrated motion as a spring-damper system plus a learned "forcing" term. The motion can then be replayed from a new start to a new goal while keeping its shape. We use it to bend a human demo so it starts at a failure's root and ends at the goal.
STAC
Sentinel's temporal action consistency score (Agia et al., CoRL 2024). It samples several action plans per call and measures how much consecutive plans disagree on the steps they share. High disagreement means "erratic". It is a runtime failure detector.
Sim-to-real / real-to-sim
Sim-to-real: whether something learned or measured in simulation holds on a real robot. Real-to-sim: rebuilding a real workspace in simulation from camera frames (objects, poses, physics, camera).
Held-out
Episodes, start states or scenes that no training step saw. A fix only counts if it helps there.

2 · What a task is

A task is not a single golden trajectory. It is a starting scene, an instruction, a check on the end state and a time limit. Any motion that ends with the check true within the limit is a success. A reference demonstration is a separate thing. We need one only to train a policy or to bend into a corrected demo with a DMP.

LIBERO writes all of this in a BDDL file (a PDDL-style problem file). Abridged from the Spatial task above:

(define (problem LIBERO_Tabletop_Manipulation)
  (:language pick the akita black bowl between the plate and the ramekin and place it on the plate)
  (:regions (between_plate_ramekin_region (:target main_table) (:ranges ((-0.06 0.19 -0.04 0.21)))) ...)
  (:fixtures main_table - table  wooden_cabinet_1 - wooden_cabinet  flat_stove_1 - flat_stove)
  (:objects akita_black_bowl_1 akita_black_bowl_2 - akita_black_bowl  plate_1 - plate ...)
  (:obj_of_interest akita_black_bowl_1 plate_1)
  (:init (On akita_black_bowl_1 main_table_between_plate_ramekin_region) (On plate_1 main_table_plate_region) ...)
  (:goal (And (On akita_black_bowl_1 plate_1))))

The :init regions are small sampling boxes, and each episode draws a fixed initial state from a list that ships with the benchmark. The robot start, cameras and lighting come from the environment code, not the BDDL. LIBERO-Plus perturbs exactly those. The time limit comes from the harness. The other suites use the same format with other goal predicates: In (basket, drawer), Open/Close and TurnOn. Some LIBERO-10 tasks have two goal stages.

Source: third_party/LIBERO-plus/libero/libero/bddl_files/libero_spatial/ (a LIBERO-Plus variant of the original LIBERO file; same format). Time limits: vla_harness/envs/libero_env.py, PORTABILITY_LIBERO_MAX §1.

6 Mechanism Localise why the policy failed by swapping parts of its input for their unperturbed versions, inside the model, and measuring how much of the change in the action each part undoes (image vs state tokens; agent camera vs wrist camera). Then find when the outcome is decided by executing a correct action chunk at call k and seeing whether the episode is rescued. works on perturbations
Runs done, per perturbation type:
  • Every perturbation reaches the action through the image tokens; the robot-state token is nearly inert.
  • Start pose: carried by the wrist camera. Restoring only the wrist image undoes a median 0.88 of the change in the first action; restoring the agent view undoes 0.17. Decided at the first model call: the correct first chunk rescues 20 of 24 failures, a plain re-run 0 of 22.
  • Camera viewpoint: agent view (0.98). Decided throughout the episode, so one corrected first chunk is not enough.
  • Sensor noise: a single camera (agent view, 0.97). Layout: agent view (0.55); a corrected first chunk does not rescue it.
  • Lighting, texture: both cameras jointly; neither alone reproduces the effect.
Limits: validated only on perturbation-induced failures; whether it carries to other failure types is untested. It needs the model's weights (it splices internal tokens) and an unperturbed twin episode.		 done; generalisation: res22 is researching failure modes beyond perturbations RESULTS.md R-036, R-037, R-039 (pathway); R-041, R-042, R-044 (wrist); R-048, R-049, R-051 (per row); R-050, R-053, R-057 (when decided); PERTURBATION_MAP.html; MINING_SPEC_DESIGN D7

Bend each demo's remaining motion from the root to the goal with a DMP, and execute it through the normal controller. Keep it only if the task succeeds and it passes jerk, speed and "nothing else knocked over" checks. Baseline: a linear bridge into the demo. PoC UNVERIFIED

3b · Scene generation from a real recording, in detail

This expands step 1 of the loop: how one real robot recording becomes a MuJoCo scene that a policy can run in. The test inputs are episodes from DROID, a public real-robot dataset. Each episode has a video from a fixed exterior camera plus the robot's recorded joint angles. Everything here runs on our 8 GB machine, mostly on CPU. All of it is exploratory code from session res31 UNVERIFIED.

What each block does

In the fourth column, blue says why the block is there and amber lists its known limits.

BlockTakes inGives outWhy it is there · Known limitsCode
1 VLM object list
candidate, not wired		 One video frame and a fixed prompt: "list every separate physical object on the table … answer only with JSON". A JSON list of objects: name, colour, count.
Why The detector (block 2) needs a name for each object it should find. A VLM can supply the names for a scene nobody has looked at.
Limits Not wired in: today the names are written by hand, and the VLM list is only compared against them. On the main test scene, Llama 3.2 11B (via NVIDIA NIM) listed the bowl, apple and cubes but called the radish a "green onion" and repeated one row.
 vlm_objects.py; runs/real2sim/ep_c3/vlm_objects_*.json
2 Grounding DINO The frame plus one text prompt per object, e.g. "black bowl", "toy block". A bounding box and a confidence score per prompt. In cluttered scenes, every instance of a prompt.
Why An open-vocabulary detector: it finds any object you can name, with no training on our scenes. Each prompt runs on its own, so similar names don't get merged. For repeated objects (8 blocks), overlapping boxes are pruned, and boxes that cover over 15% of the image or contain two other boxes are dropped.
Limits It finds only the objects it is given names for. Scores can be low (the gripper scored 0.31).
 perceive.py (grounding-dino-tiny)
3 SAM The frame plus each box from block 2. A pixel mask per object.
Why A box also contains table and neighbours. The mask gives exactly the object's pixels, which block 7 turns into 3-D points and which also give each object's real colour.
Limits An object hidden behind another gets a cut-off mask, so its fitted shape is cut off too.
 perceive.py (sam-vit-base)
4 MoGe-2 The same single frame. No depth camera is needed. A 3-D point for every pixel, in metres, plus an estimate of the camera's intrinsics.
Why This is what makes one RGB image into 3-D geometry, with no depth camera.
Limits Its overall scale can be well off: on the main test scene the scale anchor (block 6) shrank it by a factor of 0.69.
 perceive.py (moge-2-vitl-normal)
5 Camera calibration Robot masks (blocks 2–3 run on "robot arm", "robot gripper") in about 7 frames; the recorded joint angles; the camera's factory intrinsics; the dataset's rough camera pose as a start. The camera's 6-D pose relative to the robot (calib.json) and an overlay image to check it.
Why DROID's recorded camera poses are noisy, and with them the sim arm drew offset from the real one. The fix renders the sim robot at the recorded joint angles and moves the virtual camera until its outline matches the real robot's. For datasets with no camera pose, a coarse search finds a starting pose.
Limits Outline matching alone left the table tilted 13.5°. An optional level-table cost cut that to 0.02°, while the outline overlap moved from 0.425 to 0.404. That cost assumes the robot base and table are level.
 calibrate_cam.py; commit 34d22a2
6 Scale anchor The calibrated camera, the joint angles at one frame, and MoGe-2's depth on the robot's pixels. One global scale factor for MoGe-2's points (0.69 on the main scene).
Why The robot's true size is known exactly, so its depth in the sim render tells us what MoGe-2's depth should be. One factor corrects the whole scene.
Limits About 5 cm of depth-scale error still remains: in a grasp check the gripper's pinch point sits a median 5.1 cm below the cart top.
 build_scene.py (--scale anchor); scene_fit.json; commit 34d22a2
7 Build scene Masks and scaled 3-D points per object; the calibration; an asset library (LIBERO and LIBERO-Plus objects, or none); the DROID robot model (Franka FR3 arm + Robotiq 2F-85 gripper, from MuJoCo Menagerie). A MuJoCo scene (scene.mjb, scene.xml), a fit report (scene_fit.json) and a projection overlay.
Why Turns masks and points into bodies MuJoCo can simulate. The table becomes a box at the fitted height. Blocks become boxes sized from their top-face points, using the 5th–95th percentile so stray points don't inflate them; "block"/"cube" labels are made cubic. The bowl is LIBERO's black bowl scaled to the fitted rim. Other named objects (apple, radish) are retrieved by name from the library.
Limits Masses come from set densities, because mass can't be seen. Retrieved objects collide as one convex hull, because their hundreds of collision parts overflowed MuJoCo's contact memory, so any cavity is filled. Unrecognised objects are only ellipsoid stand-ins. The LIBERO-Plus assets are research-only (§3 step 1).
 build_scene.py; commit 47b46ef
8 Physics checks The scene, plus either the recorded joint trajectory or targets computed from the sim's own object poses. Metrics and a sim video next to the real one.
Why Bad geometry shows up as physics failures, so three checks run: settle (do objects stay put when nothing touches them?), replay (the real joint trajectory played through the sim's position control) and scripted grasp (an inverse-kinematics expert planned in the sim scene).
Limits Settle moved objects 0–2 cm on the main scene. Replay of the real trajectory fails on the first test episode (cause not established). The scripted grasp put 3 of 3 blocks into the bowl in clutter, but it is a scripted expert, not a VLA.
 replay.py, scripted_grasp.py; commits 7e772e0, 770dee7
9 Appearance The real video, the calibration, the masks and a sim run. A composite video: the sim robot and objects drawn over the real background, with matching shadows and colours. Optionally a Blender (Cycles) render.
Why Policies act on pixels, so a sim that looks unlike the real camera can change results by itself. Background: the per-pixel median of the video (a clean plate), with the real objects inpainted away (LaMa). Colours: each sim object gets the real median colour of its mask. Light: a directional light fitted to the real robot's shadow.
Limits On the main scene the shadows were too faint to fit a light direction (overlap 0.08), so an overhead light is assumed; only the shadow strength (0.89) is measured. The licence of LaMa's training data is unchecked.
 calibrate_light.py, composite.py, export_usd.py, blender_render.py; light.json
10 Task generation The built scene and its object list. Language tasks, randomised variants ("cousins": objects jittered in position and yaw), and a scripted-expert episode per variant: video, joint states, actions, instruction, success.
Why Turns a scene into a task set (§2) and into training data. Task types: "put the <colour> block in the bowl", "stack … on …", "move … next to …". Success is checked on the sim state. Over 2 scenes it made 21 tasks; the expert succeeded on 89 of 105 variants.
Limits Radish 0/5 (bad grasp shape); "next to the bowl" 1/5 (lands 8.5–10 cm from the rim against an 8 cm threshold). Only three task types. The episodes come from a scripted expert, not a VLA.
 make_tasks.py, tasks_page.py; runs/real2sim/tasks/summary.json; commit ca9da98

Other input sources: lerobot_episode.py converts an episode from a LeRobot-format dataset (e.g. an Open X-Embodiment Franka set) into the same folder layout, so the same blocks run on it. 5 · One worked failure

A real failed episode from our start-pose grid. The task is the Spatial scene "pick up the black bowl between the plate and the ramekin and place it on the plate", with the robot's start pose perturbed by 0.2 rad. All numbers below come from the logs and the DMP PoC, and are UNVERIFIED.

What happened. At step 31 the gripper closes 7.9 cm from the bowl's centre. The bowl lifts 2.1 cm and slips back by step 52. The policy re-grasps four times, gets a real lift at step 201, carries the bowl to the plate, and releases it at step 242. The bowl comes to rest 5.2 cm off the plate centre, and every one of the 544 successful runs in this grid ends within 3.0 cm. Two small re-grasps follow, and the episode times out at 280.

The mechanism. This is a start-pose failure, the perturbation type whose mechanism is localised (§3 step 6): the wrist camera carries it, and the outcome is decided at the first model call. The visible events at steps 31 and 242 are where the failure shows; the localisation says it was set up by the start. That is why the corrected-start data (a good first chunk) and the root-anchored DMP data are different fixes for the same episode, and which one helps more is not yet measured.

The fix, as data. Under the first-failure rule, the corrected demo shows a clean approach and grasp from the bad close at step 31. Under the first-unrecovered rule, it shows a placement correction from step 241. Both are kept by the checks UNVERIFIED. Neither has been used to retrain anything.

Sources: R-047 rollout row 14 (scene 984, joint radius 0.2 rad, direction seed 1); MINING_SPEC_V1_DESIGN §3.5; DMP_POC_SHOWCASE scenarios A and B. Distance at step 31: 7.9 cm is the full 3-D gripper-to-bowl distance from the offset (−6.84, −3.63, +1.31) cm. Elsewhere "6.8 cm short" quotes only its first component.

6 · Recommended order

Connect the links on LIBERO first. Scenes, the policy and failure collection already work there, and the true sim state is free, so every later step can be checked against truth. Add rebuilt real scenes only once a VLA has been shown to run in one.

5Run a VLA in a rebuilt real scene; give real scenes a task setThe policy behaves in the rebuilt scene as on LIBERO; depth error and asset licence resolved

LIBERO-MAX numbers count only after the paper's GR00T result reproduces (paper: 69.3% Base vs 50.0% Dynamic on Max, 69.3% vs 51.4% on Lite). Our pilot is a different subset, so it does not test this yet.

7 · Other uses of sim scenes

A simulated copy of a deployment is useful beyond the loop. What transfers from sim to real is known roughly: the ranking of policies and which perturbation hurts most transfer well (published correlations r ≈ 0.86–0.98). Absolute success rates and the size of each effect do not. So uses that rely on absolute numbers or close appearance need high-fidelity scenes. Uses that need only plausible geometry are less fidelity-bound.

UseWhat it givesFidelity needed
Deployment-matched regression testsA fixed test set that looks like the customer's cell; run on every new policy versionhigh
Reproducing field failuresRe-create a reported failure, then restore its saved states to localise it and generate correctionshigh
Sensitivity mapsWhich conditions break the policy, and in what order. Example: the LIBERO-MAX pilot shows Dynamic events cost 25 points on Spatial UNVERIFIEDhigh
Sales demos"Your cell, your failure, fixed", shown side by side with the real videohigh (appearance matters)
Site planningReach, clearances and camera placement before installationmedium (geometry yes, appearance no; brain's judgement)
Ground-truth labels for training a labellerUnlimited free labels (held, on plate, contact) from sim statelower
Calibrating failure detectorsKnown failure times to set alarm thresholds and false-alarm rateslower
Safety pre-checksCollisions, joint limits and workspace violations before a policy touches hardwarelower
