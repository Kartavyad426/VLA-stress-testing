Porting the experiments to LIBERO-MAX

impl, 2026-10-14 · for prim / the user · CPU inventory only: no code changed, nothing run. Source: a read of the scripts in the worktree VLA-exp-rootsignals (branch exp/root-signals) and in main, plus impl2's LIBERO-MAX scoping answers (10-14). Tags: V read in code, a manifest or a paper · I my inference or estimate.

Verdict.
  • Most of our code is not tied to LIBERO-Spatial's task logic. The harness already knows all four suites: step caps, BDDL region→body resolution and the instruction cleaner V. Most of the Spatial lock-in is in the analysis scripts, through four assumptions.
    1. The target is "the one object whose name doesn't contain plate".
    2. The goal is "target on the plate".
    3. The policy executes 16 steps of a 40-step chunk.
    4. Paths and scene IDs are hard-coded to R-047 (and to one task's 50 demos for E4/E6).
  • Three LIBERO-MAX facts change things beyond renaming.
    1. LIBERO-MAX runs its own runner, not libero_env.py.
    2. The paper's GR00T probably executes 8 of 40 steps per forward, not 16.
    3. Each case is a Base/Dynamic pair with a mid-task event. Objects can move after t = 0, and the Base arm is already perturbed.
  • Recommendation: first, one per-task config and one rollout format that LIBERO-MAX writes from the start (about 3 days). Then port in this order: R-059 scorers and the E1/E2 timing analyses, then E7, then the mining-spec rules. The rules are the largest job, because LIBERO-MAX brings success templates other than pick-and-place.
  • Total estimate: about 13–19 impl-days I. This excludes GPU runs, val checks and the extra checkpoints.

Shared code these all sit on

  • vla_harness/envs/libero_env.py already handles the four suites:
    • MAX_STEPS for each suite;
    • _resolve_body for region goals;
    • _clean_instruction for libero_10 scene prefixes.
    It does not handle mid-episode events. LIBERO-MAX bypasses it, per impl2's plan.
  • _gt_object_pos holds the BDDL obj_of_interest only. _gt_scene_object_pos holds every movable body. Distractors added by a distractor_burst event would appear only if logging is per step and reads the live body list.
  • poc_toy_common.py: TARGET and NEIGHBOURS are the toy task's bodies, and LIFT_M 0.05 / WINDOW 40. It is used by E2, E3 and E6 for the grasp anchor.

5 · One rollout format: AGREED (10-14)

Status. impl2 agreed to the format sent to them on 10-14, with 7 changes. The user approved all 7 (via prim, 10-14), plus checkpoint_revision and the frame policy below. LIBERO-MAX keeps its own files (cases/<id>/…), which their aggregator needs; this format is written in addition, for each arm. It is built only once a LIBERO-MAX run is approved. Every GPU run still needs prim's OK. Lines marked [A1]–[A7] are impl2's amendments.

  the frames the POLICY saw (post-flip, as passed to the policy), agent + wrist, at every policy query;
  360 px at t_event ± 1 and at grasp-onset queries, 256 px elsewhere;
  per frame: t, camera, px (resolution recorded per frame), reason ("query" | "event" | "grasp_onset")

Why these fields:

  • _gt_goal_predicates means no analysis re-implements a predicate (the 10-12 check_ontop bug class).
  • forward_env_steps and H/Q remove the hard-coded 16.
  • Stored policy-view frames remove the replay that broke E7 twice.
  • impl2's amendments, in order:
    • [A1] the case key is unique across Lite's 598 Plus/PRO variants;
    • [A2] camera, noise, lighting and theme events have no object, and distractor_burst inserts five;
    • [A3] an unreached trigger stays in the denominator, and stale-action exposure is reported separately;
    • [A4] there is one clock;
    • [A5] the Dynamic arm runs in a fresh env, and identical actions don't prove identical sim or renders (R-060);
    • [A6] control-replay queries make no prediction;
    • [A7] PNG at 360 px would be about 10–20 GB for Lite.

7 · Open points

  • Checkpoint and Q. If we run LIBERO-MAX with our lerobot checkpoints at Q = 16, it is not the paper's setting (Q = 8). If we use Isaac-GR00T's, the multi-draw wrapper must be redone. Which one the paper used is not settled. It has to be read from LIBERO-MAX's result artefacts.
  • Spatial step cap: LIBERO-MAX says 220 and we use 280. To compare with the published 69.3 / 50.0, use theirs.
  • Base arm is perturbed. Calibration sets ("successes still running", the bandwidth pool) come from the Base arm. They are not nominal, unlike R-047's radius 0.
  • MuJoCo 3.2.6 vs 3.3.2. Every frozen fit is re-derived, not carried over.
  • Nothing here has been run or changed. Every code change listed waits for the user's approval.
