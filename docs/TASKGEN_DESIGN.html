3b · Geometry comes from sim truth

User: "how will agent reason with existing geometry and sizes of base objects"; "numbers are from sim truth I guess?". The agent doesn't reason about geometry: it names intent; the tools answer every fit and placement question from the compiled model's collision geometry. scene_fit.json is used for meaning only (kind, colour name). For blocks the fit and the sim agree (fitted half-size = box geom size); for the bowl they don't: bowl_asset() takes the radius from the collision boxes' centres, not their outer edges (from the code; not measured). Neither is real-world truth (K2: size methods disagree 8–25%; K3: wrist offsets 0.7–1.9 cm), so a margin around base objects is proposed (D8).

3c · Why MuJoCo doesn't warn about overlaps

User: "why does mujoco doesn't like give warning where object meshes will be colliding?". MuJoCo's compiler doesn't check initial interpenetration; contacts are found only while simulating, and an overlap is a deep contact the solver pushes apart (a jump, or instability if large). Its runtime warnings (d.warning) cover contact-buffer overflow and bad accelerations, not overlaps. Visual-only geoms (contype = conaffinity = 0) never collide, parent/child bodies don't collide by default, and each mesh collision part is convex. So TaskGen checks overlaps itself (§3d).

6 · Stage 4 · Variation (placeholders, PnC)

User: "my idea is that everything be a placeholder, we make some preset tasks to showcase and then user takes it from there"; "lets say task is to stack blocks in order red, blue, green. Then this order be a placeholder and variations generated by PnCs".

Design. Every field of both rubrics is a slot with a type, a domain and a default. A task is a filled template, whoever filled it. Variations come from expanding the slots' domains by permutations and combinations.
template: ordered_stack
  slots:
    colours : choose 3 from {red, blue, green, yellow, orange}     scene slot
    order   : permutation of colours                               task slot
    seed    : 0..4 (placement)                                     scene slot
  instruction: "stack the blocks in order: {order[0]}, then {order[1]}, then {order[2]} on top"
  pass_condition: ordered_stack(order)
Slot kindExamplesEffectNote
Task slotorder, target, container, relationinstruction + pass condition only; same scenetests language following (like checklist F4)
Scene slotcolours, counts, sizes, seed, drawer open/closeda new scene config; scene checks re-runvariants differing only in seed share one compiled model (§12c disk)

Counts (D9, yes): each template reports how many variants are possible in total, then samples up to the cap. E.g. 3 fixed blocks: 3! = 6 orders; 3 of 5 colours ordered: 60; × 5 seeds: 300. Each variant records its slot values, so results can be split by slot. Filtered automatically: infeasible (place says why), trivial (E2), unsolvable (E1), indistinguishable colours (the real "green" block is teal, K4; palette fixed and well separated).

Existing code: make_tasks.randomise jitters all free objects ±3 cm and blocks ±0.5 rad, rejecting bounding-sphere overlaps; it moves base objects, ignores relations and checks no physics. TaskGen's variation re-runs place() with a new seed on added objects, keeping relations; the seed convention (seed·1000 + task·100 + variant) is reused.

11 · Rules every task follows

  • The base scene is locked for the agent; only added objects are resized, within bounds, every resize logged and reported.
  • Infeasible is an answer, with the reason; never a silent change.
  • Everything goes through the config, rebuilt through the simulator's editing API. Never patch a compiled .mjb (10-23: stale collision bounds).
  • Geometry questions use sim truth, with a margin for the base's fit error.
  • No overlaps at the start; nothing moves more than the settle limit; no simulator warnings.
  • Added objects on the table, inside the camera-covered area, reachable.
  • A task enters the manifest only after its checks and the user's approval, whatever its source.
  • Numbers from new code are UNVERIFIED until checked.
