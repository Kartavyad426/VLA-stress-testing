0 · Verdict

The user picked four directions on 10-19. All four can be done with what we have, and three of them start on CPU.

  1. Cheaper evaluation (§1). Cut episodes that are likely to fail and count them as failures. On our start-pose set, every failure runs to the timeout and uses 51% of all model forwards V UNVERIFIED run. A perfect cut at forward 4 would save at most 39% of forwards. The real saving depends on how many successes the cut also kills (false positives). Reducing those is a separate sub-problem, set up here for a literature review.
  2. Retraining from failure scenarios (§2). Scope not decided by the user. Every option is listed under one heading: SFT on DMP corrective demos, SFT on scripted-expert demos, failure-seeded RL, human intervention data, a broad-coverage control, and a parameter-only fix. They share one need: a held-out re-test design, which does not exist yet.
  3. Retraining data audit (§3), internal first. A pre-flight check every retraining run must pass. It covers which failures are targeted, which layers are trained, how much new data there is against the original, and style gaps (teleop vs sim, DMP vs scripted). Our negative pilot (R-056) failed on at least four of these items, and each one could have been seen before training.
  4. A public failure dataset with roots, plus a benchmark (§4). LIBERO first: the four suites we have checkpoints for, plus LIBERO-MAX. Both root rules ship, marked active development. The benchmark compares GR00T N1.7 base with our fine-tunes. No public dataset labels where a failure is decided (res21, 10-12), so this would be the first. §4c makes the case for open release and peer review to the executives. That is the user's proposal and not yet approved.

Start first: §1's CPU replay on logs we already have (about 2–3 agent-days, no GPU). In parallel, run §3's audit backwards on R-056/R-058, to check it would have flagged that pilot (about 2 agent-days, CPU). Both feed §4: §1's cut rule becomes a benchmark task, and §3's audit gates every fine-tune that §4b compares.

1 · Cheaper evaluation: stop episodes that are likely to fail

1.1 What it builds on, and what is new

Builds on: the progress signal from STAC_GROOT_THEORY §4, which is the drop in gripper-to-target distance over the first forwards. It gave AUROC 0.91 as a success signal by forward 4, and held within every radius band UNVERIFIED. Also the paired-seed scoring used since R-053, and the conformal calibration code in r059_score_c.py.

What is new: earlier docs treat the progress signal as a guardrail, an alarm on a robot (the "failure early warning" direction already noted). Here it is an evaluation-cost tool. In simulation we stop a rollout once it is predicted to fail and record it as a failure, which saves GPU time on every sweep, retraining eval and benchmark run.

An asymmetry favours this. Cutting a success early saves little, because successes are already short (median 7 forwards). Cutting a failure saves up to 14 forwards. So a cut rule can be conservative, firing only when the signal is very confident, and still save most of what is available.

1.3 The cut rule, and the false-positive sub-problem

Scoped as the user asked: a cut episode counts as a failure. Every success that gets cut is a false positive, and it biases the measured success rate downwards. Reporting and lowering that false-positive rate is a separate sub-problem. It is marked for literature review, starting from:

WorkWhat it offers this sub-problemRead depth
FIPER, "Failure Prediction at Runtime for Generative Robot Policies" (2510.09459)Conformal calibration on successful rollouts, bounding the chance that a new success is flagged as a failure. That bound is exactly our false-positive rate.search summary
Foresight (2606.23085)A one-sided, time-varying threshold from successful calibration rollouts. A per-forward threshold suits a cut at forward k.search summary
Hide-and-Seek (2605.30834)Bounds the trajectory-level false alarm rate under exchangeability. The authors note this holds only approximately on unseen tasks.search summary
Katz et al., RLC 2026 (paper)A conformal early-warning wrapper with a user-set lead timesearch summary
"Beyond Binary Success", RSS 2026 (2603.13616)Anytime-valid sequential comparison of policies, with up to 70% less evaluation effort. Fine-grained progress separates policies faster than binary success. This one stops the campaign early, where ours stops the episode, so the two stack.abstract / search summary
Snyder et al., RSS 2025 (2503.10966)Sequential tests for binary outcomes. Reported savings differ between versions (32–40% fewer trials), so check the version before citing a number.search summary
SC3-Eval (2606.18610)Early termination inside a world-model evaluator. Tightening its threshold raised terminations from 4.88% to 10.22% and lowered in-distribution correlation from 0.984 to 0.941. The cost of cutting shows up there too.search summary

I found no paper that cuts individual sim rollouts on a predicted failure to save evaluation compute (one standard search). Treat the niche as probably open, not as checked.

1.4 First proof of concept and cost

  1. CPU replay on existing logs (C1, then R-047's 720 rollouts). Compute progress per forward toward the instruction's target. Set a per-forward conformal threshold with each scene left out of its own calibration, as r059_score_c.py already does. Report forwards saved against the false-positive rate, and the bias in success rate at each threshold. About 2–3 agent-days, 0 GPU I.
  2. Live check on one new sweep. Cut by the rule, but let a random 10–20% of cut episodes keep running, so the false-positive rate is measured rather than assumed. A few GPU-hours through prim's gate I. New numeric code goes to val before any number travels.

1.5 Why it matters

  • Us: our single 8 GB card is the bottleneck for every sweep. The LIBERO-MAX Lite run is ~8–9 h (prim, 10-19); impl2's 10-14 scope estimated 20–25 GPU-h.
  • §4: the benchmark needs many rollouts per policy, so cheaper rollouts make it cheaper to run and to extend.
  • Customers: anyone running large sim evaluations, for example the deployment-matched regression tests already noted.

1.6 Risks

  • The signal uses sim state (target position). That's fine in sim, but this tool does not carry to real robots without a vision version.
  • Calibration may not transfer to a new policy. A retrained policy may move more slowly and still succeed, which would raise false positives exactly when we evaluate fine-tunes. Recalibrate per policy.
  • On LIBERO-MAX, the Dynamic event fires at pre-grasp proximity. A cut before the event would skip the thing being tested, so the rule must not fire before the event step.
  • Our failures are all slow "no progress" timeouts (STAC_GROOT_THEORY §0). Other failure types, such as drops late in the episode, may not show low progress early.

3 · Retraining data audit (internal first)

3.1 What it builds on, and what is new

Builds on: R056_POSTMORTEM, the finetune-postmortem skill, the D20 diagnostics (first-chunk fit test, offset curve), the nearest-demo spread measure from ROOT_TO_GOAL S3, and the IDM label-quality check proposed in IDM_VLA_HORIZONS. What is new: those are all after the fact. The audit runs before training, as a gate like PIPELINE_CHECKS: no retraining run gets GPU time until its data and recipe pass. It is written so it could later run on a customer's fine-tune data. The published baseline for that later step is influence-based curation: CUPID (2506.19121, CoRL 2025) and DataMIL.

3.3 First proof of concept and cost

  1. Backtest: run items 1–8 on R-056 and R-058 from existing artifacts and check the audit flags what the post-mortem found. About 2 agent-days, CPU I. It needs no new runs.
  2. Apply forward: run it on the DMP and scripted demo sets before any §2 run. This mainly needs item 4's style profiles for each source. About 1–2 agent-days, CPU I. The audit code produces numbers, so it goes to val.

3.4 Why it matters, and risks

Why: each LoRA run costs hours on our only card, and the pilot showed that a run can be uninterpretable by its own rule. The audit is the cheapest way to avoid repeating that. Later, "why did our fine-tune not help" is a common customer question, and the audit plus the post-mortem skill is a service answer to it I.

Risks:

  • Passing the audit doesn't make a run succeed; it only removes known ways to fail.
  • Thresholds are guesses until a few runs calibrate them.
  • It overlaps with the finetune-postmortem skill. The split proposed here: the skill diagnoses after the run, the audit gates before it.

4 · A public failure dataset with roots, plus a benchmark

4a · The dataset

Builds on: R-047 and C1 rollouts with per-step state and actions, the mining-spec record format, the two root rules, R-057's correct-at-forward-k decision points, the R-039–R-051 mechanism splices, restore by replay (0.00 mm), and impl2's agreed LIBERO-MAX rollout format (PORTABILITY_LIBERO_MAX §5).

What a record would hold:

  • task, instruction, policy and checkpoint revision, perturbation and its size;
  • per-step sim state, actions and frames as the policy saw them;
  • success and termination;
  • event list with recovered flags;
  • root under both rules (first failure, first unrecovered), marked active development;
  • decision-point bracket, where an intervention measured one;
  • mechanism (which input carries the failure), where splices ran;
  • the sim state at each root, so anyone can restore it and branch.

Scope as set by the user: LIBERO first, meaning the four suites we have GR00T N1.7 checkpoints for, plus LIBERO-MAX. Our rebuilt real-to-sim scenes may follow later.

4c · The case for executives: open release and peer review user's proposal, not approved

This subsection is written for the user to put to iMerit's executives. It argues for releasing the dataset and benchmark openly, optionally with a peer-reviewed paper, and says what it costs and risks.

What it buys iMerit I:

  1. Credibility for the method. Our pitch rests on claims a customer can't easily check: where a failure began, which input carried it, whether targeted data fixes it. A dataset that outsiders can download, restore and re-score turns those claims into checkable ones, and peer review is an outside check on the method. That is the user's aim: "an open source peer reviewed thing for our whole methodology".
  2. A first. No public dataset labels decision points (§4a). Being first sets the format others compare against, and the format is our mining-spec record.
  3. Shop window for iMerit's core business. Labelled failure data is iMerit's kind of product. A public set shows the quality bar without giving away the service: the pipeline, the customer work and the labelling operation stay private.
  4. Leverage on compute. A recognised benchmark is a reason for model builders to run their own policies on it, and a reason to approve rented GPU for the cross-policy comparison (§4b).
  5. Discipline we already have. Pre-registration, reproduction gates and paired controls are already how we work (AMBITIOUS_DIRECTIONS, "What we have that others don't"). Release mostly packages that work.

Risks and how to handle them:

  • Licences, the main blocker.
    • GR00T N1.7 LIBERO checkpoints: Apache-2.0 on their model card V. The base GR00T-N1.7-3B is under the NVIDIA Open Model License V.
    • LIBERO-MAX's repo has no licence file; its ACKNOWLEDGEMENTS says users must follow each component's licence V.
    • LIBERO-Plus objects probably come from BEHAVIOR-1K, whose EULA allows no redistribution (SIM_READY_ASSET_LIBRARIES §1; provenance inferred).
    • So release records and sim states, and point to the assets rather than shipping them. Ask the LIBERO-MAX and LIBERO-Plus authors before release.
  • Showing unfinished work. The root rules are under development, and our one retraining result is negative. Ship both rules and say so. Negative results in a benchmark are normal and are part of the credibility.
  • Being scooped, or the field moving. The LIBERO-Recover labels may be released. Its scenes come from six policies' failures, but it does not measure decision points.
  • Maintenance. A leaderboard needs an owner. Budget it, or release a frozen v1 only.
  • Policy coverage. GR00T-only is a thin benchmark for reviewers. Option 3 likely needs the extra GPU before submission.

The ask, if the user takes this to executives: approve option 1 for a Spatial-first v1 now, decide on option 2 or 3 once the four suites and LIBERO-MAX are in, and pre-approve rented GPU for the cross-policy runs on that condition.
