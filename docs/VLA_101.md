# VLA 101: setups and configurations

*An introduction for people new to Vision-Language-Action models. It explains what the pieces are, how they
fit together, and which settings quietly decide whether things work. Examples come from real setups (SmolVLA on
the LIBERO benchmark) so the terms stay concrete.*

---

## 1. What a VLA is

A **Vision-Language-Action model (VLA)** is a neural network that controls a robot. At every moment it looks
at camera images, reads a plain-language instruction ("put the bowl on the plate"), checks where the robot's
own arm and gripper are, and outputs the next small movement.

It runs in a loop:

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
  observation  ──►  VLA policy  ──►  action  ──►  robot / simulator moves
  (images,                          (small arm         │
   robot state,                      and gripper       │
   instruction)                      command)          │
        ▲                                              │
        └────────────── new observation ◄──────────────┘
```

The loop typically runs **10–20 times per second** until the task succeeds or time runs out. One pass from
start to finish is called an **episode** (or rollout).

**A correction to a common assumption: VLAs aren't "simple" models.** Most are built on top of a
**vision-language model** (the kind that can describe a picture), with an extra component that turns its
understanding into motor commands. Sizes range from about 0.5 billion parameters (SmolVLA) to 3–7 billion
(GR00T N1.7, π0.5, OpenVLA). What *is* simple is the training recipe, described in §3.

### Words you'll see used for the same thing

| Term | Means |
|---|---|
| **policy** | the model that decides actions. "VLA" is one kind of policy |
| **checkpoint** | a saved, trained copy of a model's weights, usually downloaded from Hugging Face |
| **episode / rollout / trial** | one attempt at a task from start to end |
| **success rate** | the percentage of episodes that complete the task |
| **benchmark** | a fixed set of tasks plus rules for scoring them, so results are comparable |

## 2. What goes in and what comes out

### The observation (input)

| Part | What it is | Typical form |
|---|---|---|
| **Images** | one or more cameras: usually a fixed "third-person" view of the scene plus a camera on the robot's wrist | e.g. two 256×256 colour images |
| **Robot state** (also called **proprioception**) | where the robot's own body is: gripper position and orientation in space, how open the gripper is | a short list of numbers, e.g. 8 values |
| **Instruction** | the task in words | "pick up the black bowl on the plate and place it on the ramekin" |

Note that the robot state describes **only the robot**, not the objects. The policy has to work out where the
bowl is from the images.

### The action (output)

Usually **7 numbers** for a single arm:

- 3 for moving the gripper (forward/back, left/right, up/down)
- 3 for rotating it
- 1 for the gripper (open or close)

Many modern VLAs predict a **chunk** of future actions at once (say, the next 50) instead of one at a time.
The eval setup then decides how many of those to actually execute before looking again (§5).

---

## 3. How VLAs are trained

The main recipe is **imitation learning** (also called **behaviour cloning**):

1. **Collect demonstrations.** A human remote-controls the robot (**teleoperation**) through the task many
   times. Each demonstration records the images, robot state, instruction and actions at every step.
2. **Train the model to copy them.** Shown an observation from a demonstration, the model learns to predict
   the action the human took next.

In practice this happens in stages:

| Stage | Data | Purpose |
|---|---|---|
| Vision-language pretraining | web images and text | general visual and language understanding |
| Robot pretraining (optional) | large mixed robot datasets, e.g. Open X-Embodiment, DROID | general manipulation skills across many robots |
| **Fine-tuning** | demonstrations for the target robot and tasks, e.g. the LIBERO dataset | the actual skill you evaluate |

**A consequence worth understanding early:** demonstrations are almost always *successful* runs. The model
rarely sees mistakes, so it rarely learns how to recover from one. If it drifts into a situation no
demonstration covered, it often just stalls.

## 4. The pieces of a setup

Running a VLA always involves three things, and most problems live in the joins between them.

```
   ┌────────────────┐     ┌──────────────────────┐     ┌────────────────────────┐
   │  1. Checkpoint │     │  2. Glue / harness   │     │  3. Environment        │
   │  trained model │ ◄─► │  formats inputs,     │ ◄─► │  simulator (MuJoCo,    │
   │  + its config  │     │  runs the loop,      │     │  robosuite, LIBERO)    │
   │                │     │  scores episodes     │     │  or a real robot       │
   └────────────────┘     └──────────────────────┘     └────────────────────────┘
```

### 1. The checkpoint

Downloaded from Hugging Face, e.g. `HuggingFaceVLA/smolvla_libero`. Usually contains:

- **weights** (`model.safetensors`)
- a **config file** (`config.json`) declaring input names, image sizes, chunk size and so on
- **normalisation statistics**: the average and spread of the training data's states and actions (§5)

### 2. The glue (eval harness)

The code that connects model and environment. It converts simulator output into what the model expects,
converts model output into robot commands, runs the loop, and counts successes. Common choices:

- **LeRobot** (Hugging Face): `lerobot-eval` supports SmolVLA, π0.5, GR00T and others on LIBERO
- **project-specific scripts**, e.g. OpenVLA's and openpi's LIBERO eval scripts

### 3. The environment

**Simulation** is where most people start: free, repeatable, and safe.

| Layer | Example | Role |
|---|---|---|
| physics engine | **MuJoCo** | computes contacts, gravity and motion, and renders images |
| robot framework | **robosuite** | robot models, controllers, standard scenes |
| benchmark | **LIBERO** | a fixed set of tasks, starting positions and success checks |

**LIBERO** is the most common VLA benchmark. It has four 10-task suites:

| Suite | Tests |
|---|---|
| `libero_spatial` | same objects, different arrangements ("the bowl *next to* the plate") |
| `libero_object` | picking the right object out of several |
| `libero_goal` | same scene, different goals ("open the drawer" vs "turn on the stove") |
| `libero_10` (Long) | longer, multi-step tasks |

Other simulated benchmarks include SimplerEnv, RoboCasa, CALVIN and ManiSkill. Each uses its own simulator,
so settings don't automatically carry over between them.

## 5. The configurations that matter

This section matters most. **A VLA can be perfectly trained and still score badly because one of these
settings disagrees between training and evaluation. Usually nothing crashes; the numbers just come out
lower.**

Rule of thumb: **evaluation must present the world to the model exactly as training did.**

### Inputs

| Setting | What it is | What goes wrong |
|---|---|---|
| **Camera names and order** | which image goes into which input slot, e.g. `image` = scene camera, `image2` = wrist camera | swapped cameras: the model sees the wrist view where it expects the scene view |
| **Image resolution** | pixel size of rendered images | training on 256×256 but evaluating at 360×360. Measured cost in our work: **17 percentage points** on one suite |
| **Image orientation** | whether images are flipped or rotated | LIBERO's raw camera images are upside-down compared with the training data, so LeRobot rotates them 180°. Miss that and the model sees an upside-down world |
| **State format** | which numbers make up the robot state, in what order and units | e.g. gripper rotation as a quaternion (4 numbers) vs axis-angle (3 numbers) |
| **Normalisation statistics** | the training data's mean and spread, used to scale inputs and outputs to a standard range | using another dataset's statistics means every value is subtly rescaled |

### Actions

| Setting | What it is | What goes wrong |
|---|---|---|
| **Control mode** | whether an action means "move *by* this much" (**relative / delta**) or "move *to* this position" (**absolute**) | mixed up, the arm flies off |
| **Gripper convention** | whether −1 means open or closed | inverted: it opens when it should grab |
| **Chunk size** | how many future actions the model predicts at once (e.g. 50) | fixed by training |
| **`n_action_steps`** | how many of those predicted actions to execute before looking again | executing all 50 blind costs about 20–30 points on LIBERO; 1 or 10 works well. See below |
| **Control frequency** (`fps`) | how many actions per second the simulator applies (LIBERO: 20) | at the wrong rate each "small move" becomes a bigger or smaller one |

**Chunking in plain terms:** the model plans the next 50 moves. `n_action_steps=10` means "do 10 of them, then
look again and replan". Higher values run faster (fewer model calls) but react more slowly to what actually
happens.

### Environment

| Setting | What it is | What goes wrong |
|---|---|---|
| **Simulator version** | e.g. MuJoCo 3.3.2 vs 3.4.0 | new versions can change physics or lighting. In MuJoCo ≥ 3.4.0, one LIBERO task's bowl starts tilted, dropping SmolVLA from 80% to 28% on it. From 3.3.3 some floors render darker, which cost OpenVLA about 17 points on one suite |
| **Initial states** | the stored starting positions of objects for each episode | different starting states make results incomparable |
| **Settle steps** | a few "do nothing" steps after reset so objects stop wobbling (LIBERO eval scripts: 10) | too few, and the policy acts in a still-moving scene |
| **Max episode length** | step budget before an episode counts as failed (LIBERO: 220–520 depending on suite) | too short turns slow successes into failures |
| **Seed** | the random-number starting point | a different seed gives a different sample of episodes; compare like with like |

## 6. A worked example: SmolVLA on LIBERO

What a real configuration looks like, and where each value comes from.

> **Note for this project:** SmolVLA is used here only because its configuration is a clear teaching example.
> In our own work it is **vetoed**: it never reproduced its published number (RESULTS.md R-011, R-017). The
> project's workhorse is GR00T N1.7 (`nvidia/gr00t17-lerobot-libero_spatial-640`, bf16), with MINERVA as the
> reproduction control.

| Setting | Value | Where it's defined |
|---|---|---|
| Checkpoint | `HuggingFaceVLA/smolvla_libero` | Hugging Face |
| Model size | ~605M parameters | weights file |
| Cameras | `image` (scene), `image2` (wrist), 256×256 each | checkpoint `config.json` |
| Image orientation | rotated 180° | LeRobot's LIBERO code, **not** the checkpoint |
| Robot state | 8 numbers: gripper position (3) + rotation (3) + finger positions (2) | checkpoint config + LeRobot code |
| Action | 7 numbers, relative control | checkpoint config + env default |
| Chunk size | 50 | checkpoint config |
| `n_action_steps` | config says 1; 10 is common in practice and scores about the same | checkpoint config, overridden on the command line |
| Control frequency | 20 Hz | env default |
| Simulator | MuJoCo 3.3.x (below 3.4.0), robosuite 1.4 | your install, **not** the checkpoint |

A typical evaluation command:

```bash
lerobot-eval \
  --policy.path=HuggingFaceVLA/smolvla_libero \
  --env.type=libero \
  --env.task=libero_spatial \
  --env.observation_height=256 --env.observation_width=256 \
  --policy.n_action_steps=10 \
  --eval.n_episodes=10 --eval.batch_size=1 \
  --seed=1000
```

Notice how the settings are split across the checkpoint's config, the eval code's defaults, the command line
and your installed packages. **No single file holds the full contract**, which is why mismatches are so
common.

## 7. Lessons that save time

1. **A low score doesn't prove a weak model.** Before concluding a policy is bad, check resolution,
   orientation, cameras, `n_action_steps`, control frequency and simulator version.
2. **Settings fail silently.** Tools typically check that input *names* match, not sizes or meanings. A
   256-vs-360 image mismatch runs without a single warning.
3. **The checkpoint's `config.json` isn't the whole story.** Some published results use values that differ
   from the config (e.g. a different `n_action_steps`), and many settings (image flip, simulator version) aren't
   in the config at all. Look for the authors' actual eval command.
4. **Pin your simulator version.** A fresh `pip install` can pull a newer MuJoCo that changes results.
   Record the versions of MuJoCo, robosuite and LIBERO alongside every number.
5. **Run a small smoke test first.** A few episodes on one task will catch a broken setup before you spend
   hours on hundreds.
6. **Small evaluations are noisy.** 10 episodes per task (100 per suite) gives roughly ±10 percentage points of
   uncertainty. Differences smaller than that may be chance.
7. **Change one thing at a time.** Compare runs that differ in exactly one setting, with the same seed and
   starting states, so you know what caused a change.
8. **Check a published number applies to your checkpoint.** A paper's headline result may come from a
   different model variant than the checkpoint you downloaded.

## 8. Hardware, briefly

| Model | Size | Runs on an 8 GB GPU? |
|---|---|---|
| SmolVLA | ~0.5B | yes |
| OpenVLA | 7B | generally no without heavy compression |
| π0.5 | ~3.6B | no: out of memory at 7.40 of 7.53 GiB in our tests (RESULTS.md R-001, R-032) |
| π0-FAST | ~2.9B | no: four configurations tried, none fit (R-032) |
| GR00T N1.7 | 3.1B | yes, in bf16: 5.87 GiB measured (R-021). Our workhorse |

Simulation itself needs little GPU, but it shares memory with the model. On laptops, also check the machine is
plugged in: GPUs can throttle heavily on battery while still reporting 100% utilisation.

## 9. Where to start

1. Install LeRobot with its LIBERO extra, and **pin MuJoCo below 3.4.0**.
2. Evaluate a checkpoint that reproduces its published number on one task with 5–10 episodes. In this project
   that means GR00T N1.7 (`nvidia/gr00t17-lerobot-libero_spatial-640`) or MINERVA, through
   `experiments/harness_eval.py`, not SmolVLA (vetoed; see §6).
3. Watch the saved episode videos. Seeing the robot move tells you more than a percentage.
4. Change one setting (e.g. `n_action_steps`) and compare.
5. Then scale up to full suites, recording every version and setting next to the result.

## Glossary

| Term | Plain meaning |
|---|---|
| **Action chunk** | several future actions predicted at once |
| **Axis-angle / quaternion** | two ways of writing down a 3D rotation as numbers |
| **Behaviour cloning** | training a model to copy recorded demonstrations |
| **Benchmark suite** | a named group of related tasks, e.g. `libero_spatial` |
| **Checkpoint** | saved trained weights of a model |
| **Delta (relative) action** | "move by this much" |
| **Absolute action** | "move to here" |
| **Episode** | one attempt at a task |
| **Fine-tuning** | further training of a pretrained model on specific data |
| **Normalisation** | rescaling numbers to a standard range using training-data statistics |
| **Proprioception** | the robot's sense of its own body: joint and gripper positions |
| **Seed** | a number that fixes randomness so runs can be repeated |
| **Sim-to-real gap** | differences between simulated and real-world behaviour |
| **Teleoperation** | a human remote-controlling a robot, usually to record demonstrations |
| **VLM** | vision-language model: understands images and text, but doesn't control robots |
