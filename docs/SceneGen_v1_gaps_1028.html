Not built: objects inside drawers, boxes or containers; objects hidden behind another object or the robot at frame 0; objects a person brings in; the lower object of a stack. 5 · Beyond the reference episode: composed tasks and prompt-made scenes (scope, 10-28; not v1)

User: "we just need a reference scene right? … once we have made these in sim, we can have interactions like that right? Like final goal is an eval set, so a scene like drawer having 5 blocks inside and robot has to take them out and stack them color wise?" and "can we also make tasks just by prompt … I prompt it what the initial scene would look like, like table bg etc. comes from video I put in a new object or maybe multiple new object … texture would be an issue I guess tho? should we find some other way for that?"

Yes, the episode is only the reference for what must look and measure real: table, background, lighting, cameras, the robot rig. Once those are in sim, objects and tasks can be composed freely, including hidden objects (blocks inside a drawer). What each added thing needs:

NeedFor the drawer exampleSource

Proof it's solvablean expert that opens the drawer, picks, stacksscripted expert per task type (B3 generalised); "a new expert per scenario" is expected (user, 10-26)
Checksimage-physics consistency, expert solves it, do-nothing doesn'tchecklist B, D, E

Prompt-made scenes (an agent): reference episode (background, table, cameras, light) + a prompt ("add a drawer with 5 blocks inside; task: stack them by colour") → the agent picks or generates assets, proposes a layout, writes the task and success rule, the scripted expert proves it solvable, the checklist runs, the user approves in the inspector. Feasible; each step exists in some form except asset choice/generation and the generic expert.

Textures. Added objects are sim-rendered, not real pixels. Evidence so far: in the G6 image swaps, block appearance and compression did not move GR00T's plan; table texture, light/shadow and the gripper did. So object textures may matter less than feared, but large objects (a drawer filling the wrist view) are untested. Ways to get realistic object appearance, best first:

  1. Scanned asset libraries (GSO, YCB): photogrammetry textures from real objects.
  2. Objects from other DROID episodes (the ObjGen session's work): model and texture built from real footage of the object.
  3. Generated assets (text/image-to-3D): weakest textures today.
  4. Generated images (Cosmos-style transfer): heavy, needs ≥ 48 GB, loses fidelity to the source.

Whatever the source, the image swap (C6) measures whether the policy treats the added object as real. Proposed order: v1 (reconstruct, then perturb existing objects) → v1.5 (add library objects to reconstructed scenes, one image-swap check per new object type) → v2 (articulated objects, prompt-made scenes).

7 · DROID's refined calibrations (found 10-28)

DROID published higher-accuracy extrinsics after the release (data/real2sim/droid/calib/README.md): cam2base_extrinsics.json (~36k episodes, one camera each, with a quality score), cam2base_extrinsic_superset.json (~24k, both cameras), cam2cam_extrinsics.json (~90k, not downloaded). The first two were on disk and never used by the pipeline (res31's miss). Coverage of our five, camera 22008760: c9 and c1b yes ("source: GT", robot-mask IoU 0.856 / 0.795, values identical to the episode's recorded extrinsics), orange, c11, c3 no. Rendering c9 from DROID's GT camera (runs/real2sim/v1_dev/camera_search/compare/c9gt.jpg): the sim robot's base and gripper sit on the real ones by eye. Our outline score gave that camera 0.28 and our search moved 12 cm / 6° away from it, because of #16 (motion masks) and #11 (the cup gripped at its rim; first written here as the mallet's handle, corrected after drawing the grasp on the frames: runs/real2sim/v1_dev/camera_search/compare/c9gt_grasp.jpg).

Proposed design change (awaiting the user): keep the approach (robot as origin, geometry from grasp points and the wrist, scripted expert = doable, real pixels for backgrounds); take the camera from DROID's refined calibration whenever it exists (quality ≥ ~0.8) and select v1 scenes from those ~36k episodes; our checks (drops in containers, table level, wrist offsets, the user in the inspector) verify it; the camera search only for episodes without one (it worked on orange). Fix #16 and #11 regardless.

11 · Changing the simulator: what it touches and how much work (10-30; user: "if we need to change simulator then how much effort is it, what all changes need to be done")

Written 2026-10-30 00:53 by res31. Module counts and MuJoCo usage were read from the code. Facts about other simulators come from SIM_ALTERNATIVES_PIPELINE.html (res21, 10-06), which checked them; this section adds nothing new about them. The effort figures are my estimates, not measured.

Verdict. The scene description is already simulator-neutral: the objects and table (scene_fit.json), the camera (calib.json), and the redaction and inventory lists. Everything that uses the scene is MuJoCo-bound, though: assembling the model, the robot's fingertip positions, physics, rendering, the scripted expert and policy rollouts. 38 of the 52 modules in experiments/real2sim/ import mujoco.
  • Full switch: about 6–10 person-weeks across res31, implres31 and TaskGen, plus GPU time to redo every policy baseline (estimate).
  • Rendering-only switch (MuJoCo keeps the physics): about 2–3 weeks, and a first version of it already exists (MuJoCo → USD → Blender).
  • Choice of simulator: Isaac Sim does not fit this machine. Its minimum is a 16 GB RTX GPU, and we have an 8 GB RTX PRO 1000.

TaskGen already keeps its framework behind a simulator interface (core/sim.py, an abstract Sim class; sim_mujoco/ implements it). Using that same interface in SceneGen is the natural first step.

11b · Asset and physics issues that don't show up in line counts

  • Robot gripper: the Robotiq 2F-85 model is a closed linkage held together with a tendon and equality constraints (Menagerie 2f85.xml). Other simulators model these differently; the gripper has to be re-authored and its grip re-tested.
  • Objects: LIBERO models are MuJoCo XML files (meshes plus collision boxes). res21 recorded RoboVerse's note that a port to SAPIEN/Newton "needs asset re-authoring + a different contact model", which makes it approximate, not 1:1.
  • Contact and friction: per-object friction triples (MuJoCo's sliding/torsion/rolling) and the elliptic friction cone set in rollouts do not carry over one-to-one. Slip, lift and settle results would all shift.
  • Baselines are MuJoCo-only: res21 recorded ROBOGATE's result that a GR00T N1.6 LIBERO checkpoint scored 97.65% in MuJoCo and 0% on Isaac Sim scenes. Every policy result so far would need re-running before any comparison.
  • Hardware: Isaac Sim 6.0 needs at least an RTX 4080 with 16 GB VRAM (res21, verified). This machine has an 8 GB RTX PRO 1000. Isaac means a rented GPU.
  • MuJoCo Warp (a GPU MuJoCo) is not a simulator change. Our real2sim venv is MuJoCo 3.15.0, which meets its ≥ 3.12 requirement. The LIBERO venvs stay pinned below 3.4.

11d · Recommendation

  • Decide by the reason for switching. If the reason is how the scenes look (gripper appearance, lighting; see the 10-29 wrist flicker), switch only the renderer. The USD → Blender path is the start of that. MuJoCo keeps the physics, the checks and all baselines.
  • Switch the physics only if contact or grasp behaviour is the problem, and expect items 2–11.
  • Either way, item 1 first: putting SceneGen behind TaskGen's simulator interface costs little and makes a later switch a new backend, not a rewrite.
