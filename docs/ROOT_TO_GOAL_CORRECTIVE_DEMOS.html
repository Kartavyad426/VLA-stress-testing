Root-to-Goal Corrective Demos (DMP retargeting)

2026-10-12 · session res, from the user's proposal · outline approved by the user 10-12 · for prim · no code yet

Status: proposal. Nothing here has been run. All costs are estimates. Any number this pipeline produces must pass val before it counts, so it is UNVERIFIED until then. The open questions in §5 are for the user and prim.

0 · In one paragraph

For each failed rollout, find its root state: the first unrecovered event (ROOT_IDENTIFICATION). Take the most similar clean human demo at the same phase. Retarget that demo's remaining motion from the root to the goal with Dynamic Movement Primitives, so the motion keeps the demo's shape, speed and gripper timing. Execute it in the sim through the controller, so actions are recorded exactly. Keep only successes and co-train on these root→goal corrective segments. No video model is needed, and the IDM is used only as a checker, not a labeller.

1 · Why this and not DreamGen

  • DreamGen (2505.12705) uses a video world model to imagine new situations, then an IDM to guess the actions. That is a substitute for a simulator. We have the simulator, which gives exact actions and an exact success check.
  • Cost: DreamGen RoboCasa took about 54 h × 1,500 L40s. A scaled-down pilot would need roughly 200–1,000 cloud GPU-h (res estimate, not measured). This proposal runs on CPU plus the 8 GB card.
  • Our failures are start-pose failures decided at forwards 0–1 (R-044, R-057). R-056 showed that coverage matters, not volume, so data has to start where the policy goes wrong.

3 · How it relates to what we already have

  • D21 (open): Option A bridge-and-join (MimicGen-lite, FLARE-style bridging) vs Option B scripted expert with DART noise. This proposal is a variant of Option A. It starts at the policy's own root instead of at a perturbed start, and it uses a DMP instead of MimicGen's rigid transform plus linear interpolation. prim should decide whether it replaces Option A, is part of it, or is separate.
  • MINING_SPEC D14: the success search already matches "a snapshot of the situation at the root". S3 could be that search, and the two should share code.
  • R-054 rescue minting: dropped on 10-06 because yield was about 0.2 beyond 16 cm. S6 has to report yield by offset band from day one, so we find out early whether DMP retargeting does better at large offsets.
  • IDM_VLA_HORIZONS T0/T1: these are S0 and the IDM for S7. Nothing else involving an IDM runs before T1 passes.

4a · IntervenGen side by side full paper read in the arXiv PDF (v1); website extras not read

IntervenGen (I-Gen) is the closest prior work, so I read its generation method directly. Its loop: run the base policy in a new scene with a fresh observation corruption until contact detection flags a mistake. Pick a random human intervention, transform its recovery segment to the current object pose, linearly interpolate the EEF to its start, and replay it open-loop. Keep the episode only if the task succeeds, and keep the recovery part, not the mistake, for training. Aggregate with the base data and retrain (BC-RNN, robomimic). The paper's claim, verbatim: "increase policy robustness by up to 39× with only 10 human interventions" (3.5× / 10.7× / 39× over base on Nut Insertion / 2-Piece Assembly / Coffee).

Novelty, honestly: this is close to "IntervenGen without human interventions": DMP bridging from nominal demos plus automatic root finding. It is a reasonable engineering variant for our setup, not a new method. If it works, the reportable comparison is against I-Gen-style linear-interpolation bridging on the same roots, which costs one extra arm in the root pilot.

The multipliers are relative improvement, (I-Gen − Base) / Base, and they match Table I: (98−22)/22 = 3.45, (70−6)/6 = 10.7, (80−2)/2 = 39. The paper's "% improvements" are absolute percentage points.

Caveats before carrying the numbers over

  • Selection: each cell is the best of 40 checkpoints (2,000 epochs, evaluated every 50), at 50 trials each. This inflates every number, most of all the noisy baselines.
  • Seeds: only Nut Insertion has a seed check (98 / 100 / 98%); everything else is a single seed. The real-robot results rest on 10 trials.
  • State-based policies: BC-RNN on proprioception plus object poses, with no images. Nothing here shows that image-based VLAs benefit.
  • Privileged information: the true object pose (or a contact hint, Table III) is given on contact, mistakes are detected by contact, and object poses are known exactly during generation.
  • Different failure type: theirs is missing information (a corrupted pose belief). Ours is a policy that hasn't seen these states, though the images contain everything it needs. Their Assumption 4 holds trivially for us, but the size of their effect may not transfer.
  • Inter-subtask recovery and "offline mode" are on the project website only; not read.

5 · Undecided questions (for the user / prim)

  1. Scope vs D21: replace Option A, sit inside it, or be a separate track?
  2. Goal definition: the end of the matched demo segment, or the end of the whole task? (This affects whether one episode covers several phases.)
  3. Match threshold and k: set from the spread of distances between demos (for example the 95th percentile) or fixed by hand?
  4. What to train on: only the root→goal corrective segment, or also the policy's own start→root prefix (for state context, with no action loss on the prefix)? IntervenGen keeps only the post-mistake part (§4a).
  5. Dose: the corrective:original ratio, pre-registered from the R-056 / D20 offset-band data. IntervenGen used 1:1 and was still improving at 5:1 (§4a).
  6. S7: worth building now, or later once T1 passes?

6 · Cost (estimate)

  • Engineering: S0–S6 about 5–8 days (DMP core about 1 day; matching and segmentation about 2; execution and filter about 2; plumbing and val checks 1–3).
  • Compute: everything up to S6 runs on CPU. S8 is a normal LoRA retrain plus eval sweep on the 8 GB card. No cloud.

7 · Cheapest first tests (in order)

  1. T0: does demo replay reproduce the demos? If not, S0 and S3 have nothing clean to match against. (CPU, about 2–4 h.)
  2. DMP sanity: retarget a demo to its own start and goal and check it reproduces itself. Then retarget to ±2/8/16 cm offsets and report success yield per band. Compare with R-054's 0.2 beyond 16 cm. Also check that jerk in the first steps after the join is within the human demos' range.
  3. Root pilot: 20 roots from one scene, top-3 matches each. Report yield, a visual match check (root frame vs matched demo frame), and coverage-gap rate. Add a second arm that uses I-Gen-style linear-interpolation bridging on the same roots (§4a).
  4. Only after these, a small S8 co-train with a pre-registered dose and val in the loop.
