Mining Spec Design

Design record, in progress · started 2026-10-08 · prim with the user · iteration 8 (D10–D15; §6c external data; §7b branching with PoC corrections; 10-08). Records what has been decided about the failure-scenario mining spec, why, and what is still open. Tags: agreed decided with the user on 10-08; proposed prim's suggestion, not yet agreed; open not yet discussed.

Bottom line so far

  • A mining spec describes the failure scenarios of one policy in one deployment setting. Each instance is precise enough to do three jobs: query a dataset, brief a teleoperator, and seed sim generation.
  • An instance is either a complete episode or the segment of an episode where the failure happens. Segments serve as sub-failures. Complete episodes are the basis for generating more demos.
  • The work splits into four pieces: a shared scenario index (built first), the mining spec (the product for now), a failure corpus of frequencies across policies and deployments built from open-source data, and a client intent spec (Phase 1 input).
  • Phase 0 specs carry no cost. Cost, severity and urgency arrive with the client in Phase 1. This is consistent with PLAN.md §9.3: we do not ship a cardinal severity without the client's prevalence.
  • A failure counts as a failure mode only inside the policy's fine-tuned domain. Outside it, it is a coverage gap (D10). The index links task-level scenarios to reusable, task-independent sub-scenarios (D11), which is what lets policies tuned on different tasks be compared.
  • The mining spec is the successor to PLAN.md §9's Data Gap Manifest. It widens a manifest row from "a perturbation boundary" to "any failure scenario, at episode or segment level, usable three ways".

1 · Intent

What the user said

  • Not all failures are equal. Some matter more to a business requirement, so we need an estimate of the loss each failure mode causes, driven by how often it appears. Each failure gets cost, severity and urgency factors.
  • A failure in a bigger task can be an aggregate of smaller failures across a range of tasks. Some of the smaller ones may not be human-interpretable.
  • For start-pose failures the spec has an initial configuration. For mid-episode failures such as a retry loop, we need to mine scenarios that contain a similar section.
  • One spec instance should let us mine scenarios from a dataset, let a teleoperator understand it in isolation and perform a successful demonstration, and generate sim data.
  • Phase 0 covers the general failures of a policy (perturbations plus possible fixes). Phase 1 starts from the client: their domain problems, the failures they most want solved, their purpose, and what they hand us (a spec request only, or a policy plus raw data to test on their deployment settings in sim). In Phase 1 the spec becomes an intermediate state rather than the final product. For now, treat the mining spec as the final product, while keeping it easy to mine from.
  • The format is ours to decide: fixed core fields, plus room for customer-domain settings when needed.
  • Our mechanism localisation is proven only on perturbations. Whether it generalises to diverse tasks is untested; res22 is researching failure modes beyond perturbations. The user expects similar efforts to generalise.
  • For now we work on open-source datasets, so we can build a corpus of failure frequencies across policies and deployment scenarios, per scenario and sub-scenario. That strengthens the offering.
  • It may become a commercial offering.

Success criteria (prim's reading, to confirm)

  • A teleoperator who has never seen our harness can read one instance and know what situation to set up and what a successful demonstration looks like.
  • The same instance, run as a query, returns matching episodes or segments from a dataset, with no human in the loop.
  • The same instance gives a sim generator enough to reproduce the situation: initial state, conditions, task.
  • Specs from different policies and clients can be compared through shared scenario ids, without exposing one client's details in another's spec.

3 · Decisions and why

#DecisionWhyAlternatives considered
D1 agreedOne instance, three uses: dataset query, teleoperator brief, sim generation recipe.One description of a scenario avoids three drifting ones. Each use checks the others: a query that finds nothing, or a brief the operator can't act on, exposes an under-specified scenario.Separate artefacts per use: rejected, because they drift apart.
D2 agreedPhase 0 then Phase 1. Phase 0 is a generic spec per policy (perturbations plus possible fixes), written by us. Phase 1 is client-driven. The spec is the final product now and an intermediate state later.Phase 0 can be built today from our harness and open data. Phase 1 needs a client. Designing for "executable later" now avoids a rewrite.—
D3 agreedA spec is per (policy, deployment setting). A new policy, or a new deployment, gets a new spec. Entries are inline and self-contained.It's the natural unit to sell (one engagement, one document). The operator and the miner need only this file. Rates and mechanism sit next to their scenario, so no join can go wrong (cf. the rollout_id join bug, D25). Versioning is simple: retest, get a new spec.A shared scenario catalogue plus per-policy assessment records (prim's first proposal). Rejected: no single deliverable, client details would sit in a shared catalogue, and it's more machinery than Phase 0 needs. D4 agreedInstance granularity: a complete episode or a segment. Segments are where the failure happens and serve as sub-failures. Complete episodes are the basis for generating more demos.Start-pose failures are decided at forward 0 and need the whole episode from its initial configuration. Mid-episode failures (a retry loop) need a window that can be matched inside other episodes.—
D5 agreedNon-interpretable sub-failures are allowed. They are used to measure the feasibility and the severity of solving a problem, treated independently of each other. A teleoperator brief isn't required for them. Whether more demos on them help is deferred; they may still be useful for mining.Some sub-failures are defined by signals a human can't see (e.g. an internal-feature pattern). Forcing a human description would invent one. Keeping feasibility and severity separate avoids ranking an easy, low-impact fix above a hard, high-impact one.Requiring every instance to be interpretable: rejected, because it would drop real failures.
D6 agreedPhase 0 carries no cost. Cost, severity and urgency enter in Phase 1 from the client. A Phase 0 spec may not even show the failures a client has in mind, and that is acceptable.Consistent with PLAN.md §9.3: P(condition) in sim is our own choice, so a cost built on it would be invented.A default cost in Phase 0: rejected.
D7 agreedMechanism is an optional block with an evidence status. It is filled where localisation has been run, otherwise marked untested.Localisation is validated only on perturbations. Its generality across task diversity is untested; res22 is working on that.A mandatory mechanism: rejected for now.
D8 agreedFixed core plus customer extensions. We define the core fields; customer-domain settings go in a declared extension area.A stable core keeps specs comparable and searchable; extensions keep the core from bloating per client.—
D9 agreedFour pieces, in this order: (1) scenario index, (2) mining spec, (3) failure corpus, (4) client intent spec. Each gets its own short design.The index is what the other three point at. The corpus is counting once 1 and 2 exist. Intent is Phase 1.One combined design: rejected, too large to settle at once.
D10 agreedCompetence domain on every instance and every corpus count. Four values: in-domain (trained task and embodiment, nominal conditions), in-domain + condition (perturbed, or a mid-task event), held-out task, same embodiment, other embodiment. Only the first two produce failure modes; the last two are coverage gaps. The corpus counts each policy inside its own fine-tuned domain, not every policy on every dataset.A fine-tune fixes the policy's whole input–output contract, not just which tasks it knows. Our GR00T LIBERO checkpoint (nvidia/gr00t17-lerobot-libero_spatial-640, config.json) has embodiment_tag: libero_sim, which selects per-embodiment state-encoder and action-decoder weights. It outputs a 7-D end-effector delta plus gripper under LIBERO normalisation, takes 8-D state and two 256 px cameras (image, wrist_image), and tuned only the projector and action head. On RoboCasa (robocasa_panda_omron, a mobile base) the shapes don't match. Failures there would mean "never trained", not a failure mode. Coverage gaps and failure modes need different fixes: a fine-tune vs targeted data, augmentation or an envelope. Testing an un-tuned policy on a diverse-failure corpus would confuse the two. Unverified: the preprocessor's embodiment list includes robocasa_panda_omron, so GR00T's pretraining probably saw RoboCasa. Whether the base model works there without fine-tuning is untested.Running every policy on every corpus scenario: rejected, because it mostly measures coverage gaps.
D11 agreedIndex with two linked axes (piece 1). Task-level scenarios ("put the bowl in the drawer fails") point at reusable, task-independent sub-scenarios ("grasp slip", "retry loop"). Non-interpretable sub-scenarios are a third kind, identified by their signature, not a name.It matches the user's point that a big-task failure aggregates smaller failures across tasks. Under D10 it is also what makes cross-policy comparison possible: policies tuned on different tasks can still be compared on sub-scenario rates within their own domains (e.g. grasp slip in 12% of in-domain episodes for X, 4% for Y).A strict tree (task family → phase → mode → condition): rejected, because the same sub-failure repeats under every task family and counting it across tasks needs a merge step. Flat tags: rejected, because they can't say "this failure is made of these".
D12 agreedA sub-scenario is identified by phase × failure mode (e.g. grasp × slip, transport × drop). Phases come from the segmenter (approach / grasp / transport / place). The triggering condition (camera shift, mid-task event…) is a separate field, not part of the identity. Clustering by condition can be done later if needed.Phase and failure mode are what can be observed in an episode and what a teleoperator can act on. The condition is a cause, which localisation may or may not establish (D7). This follows PLAN §9's rule that a symptom is "observable behaviour, not inferred cause". Keeping the condition out of the identity stops the index multiplying, and lets counts pool across conditions.Phase × mode × condition: rejected for now (index blow-up; splits one physical failure by an unproven cause). Failure mode only: rejected (loses the phase a teleoperator needs).
D13 agreedFixing is grouped by (root situation, mechanism), not by failure pattern. An instance carries:
  • root: the first divergence, as phase × failure mode (starting detector: divergence_point in vla_harness/mining/phases.py, LIBERO-only);
  • situation: the entry state at the root, with the dimensions the mechanism says to hold fixed marked as such (all of them, while the mechanism is unknown);
  • success criterion: the exit condition that defines "got past it" (e.g. object held and lifted 5 cm within N steps);
  • terminal outcome: one field, so Phase 1 can attach cost (PLAN §7b.3).
parked · not in the PoC The full failure sequence (phase × outcome events, repeats collapsed) is optional raw evidence. Pattern grammar, cycle collapsing and prefix grouping of failure sequences are deferred to the failure-corpus design (piece 3). The user is not convinced of their use, and no code for them is planned in the first PoC iteration.		To fix a failure you need successful demos of the same situation, not more examples of the same failure. Different failure patterns (e.g. miss(3) → grasp vs (miss → grasp)(3)) can share one cause and need identical demos. Identical patterns can have different causes; classify.py's _attempt_spread exists because "same point repeated" and "spread-out search" look alike in aggregate. So the pattern neither separates causes nor finds successes. The mechanism says which situation dimensions must match: what the camera sees for a vision fault, the configuration for a state fault (FAILURE_TO_DATA_PIPELINE: hold fixed vs resample).Group by the full failure sequence (ordered, cycle-collapsed, prefix-matched): parked as above. Root + consequences: subsumed.
D14 agreedSearching for successes matches a snapshot at the root, not the prefix.
  1. Filter: same task (or instruction family); the episode reached the root's phase and met the success criterion.
  2. Situation match at that phase's entry frame, over the policy's own observation window, on the held-fixed dimensions only, within tolerances. All dimensions are held while the mechanism is unknown.
  3. Return the segment from entry to exit, plus the policy's context frames before it.
The prefix (how the episode got there) is not part of the search. It is used only to reach the situation (sim state restore, teleop setup), and as an optional cheap filter where initial states are shared. An empty result is a finding: the situation is a coverage gap, and the spec falls back to producing it instead of finding it. Worked example in §6b.		GR00T N1.7 has no memory: its preprocessor has state_horizon: 1 and video_horizon: null, so the situation is fully described by one snapshot. History that matters (e.g. an earlier nudge) already shows in the snapshot. A full-prefix match would discard nearly all usable data, since dataset episodes almost never share a trajectory. A policy with history would match over its observation window, which is why the window is a field.Match the full prefix up to the failure: rejected (needlessly narrow).
D15 proposed · not yet read by the userEvery situation field records its source and uncertainty: exact (sim), estimated (model, ±σ) or unavailable. The search compares only the fields both sides have, and widens each tolerance by the estimate's error. An image-embedding match is the universal fallback for any data with images. See §6c for what each external tier needs.Outside a simulator, object pose, contacts and "holding" have to be estimated or replaced. Without a source tag, an estimated 4 cm looks as trustworthy as an exact one. Which fields can be estimated depends on the data tier (§6c). The mechanism decides whether an external tier can help at all: vision faults need appearance (embeddings, any tier); geometry faults need metric object position (tier 1, or tier 2 with depth and calibration).Treating estimated fields as exact: rejected. Embedding-only search everywhere: rejected as the default (fuzzy, hard to explain), kept as a fallback.

The four pieces

1 · firstScenario indexA shared hierarchy of scenarios and sub-scenarios with stable, versioned ids. No client details.
2 · the productMining specPer (policy, deployment). Instances are episodes or segments, each tagged with index ids.
3Failure corpusFrequency per index id across (policy, deployment), measured on open-source datasets and our sim runs.
4 · Phase 1Client intent specWhat the client has in mind: domain, priority failures, purpose, assets. Shapes which instances a spec focuses on.

2, 3 and 4 refer to 1 by id. 3 aggregates over many 2s. 4 drives which 2 gets built.

4 · Rules carried over from PLAN.md §9 proposed

  • Every instance is a claim with its evidence attached: the episodes it was observed in, the seeds, the run ids, the checkpoint revision. An instance without evidence is a hypothesis and must say so.
  • Coverage is diversity, not counts. What to mine is stated as the axes to vary (objects, scenes, poses), never "500 more demos" (§9.1, Lin et al. 2024).
  • Untested is visible. An empty mechanism or validation block renders as "untested", never as absent.
  • Fixability. Each instance says whether mining is the right remedy at all (augmentation / data / architecture / operational).
  • Sampling arm. Any frequency records whether it came from uniform or failure-targeted sampling. Only uniform-arm frequencies are comparable.

5 · Tensions

#TensionStatus
T1What a corpus frequency means. Counting a scenario across open datasets gives a real frequency only where the data is naturalistic (deployment logs, or demos as collected). On a perturbation grid, or on failure-enriched sampling, the frequency is set by whoever chose the grid (PLAN §9.3). The corpus must record its sampling and report P(fail | condition) separately from P(condition).open for piece 3
T2Non-interpretable sub-failures vs the teleoperator brief.resolved by D5: the brief is optional for them
T3Frequency before cost. The user wants loss estimated from frequency. In Phase 0 only P(fail | condition) exists.resolved by D6: loss is computed only once Phase 1 supplies prevalence and cost
T4What counts as "one policy". Is a fine-tuned checkpoint of the same model a new policy and so a new spec, or a new version of the same spec?open
T5Successor or replacement. Does the mining spec replace PLAN §9's manifest, or does a manifest row become one instance type within it?open

6 · Shape of an instance, for orientation only proposed

Nothing below is decided. It shows which blocks the next iterations need to settle, not their fields.

{
  "spec":     { policy, checkpoint, deployment, phase: 0|1, schema_version },
  "instance": {
    "id", "scenario_ids": [ index ids, parent → child ],
    "unit": "episode" | "segment",
    "competence_domain": in-domain | in-domain+condition | held-out-task | other-embodiment   (D10)
    "root":       first divergence, phase × failure mode                                    (D13)
    "situation":  entry state at the root; held-fixed dims marked                           (D13)
    "success":    exit condition that defines "got past it"                                 (D13)
    "terminal":   final outcome, for Phase 1 cost                                           (D13)
    "sequence":   optional raw evidence, PARKED                                             (D13)
    "signature":  machine-checkable definition: what makes a window match (D5: required)
    "brief":      teleoperator text, plus what success looks like (optional if not interpretable)
    "generate":   sim recipe: env, task, knobs, init states
    "evidence":   episodes, seeds, runs, P(fail | condition) with CI, sampling arm
    "mechanism":  optional, with evidence status (D7)
    "fixability", "coverage_required"
    "assessment": Phase 1 only: prevalence, cost, severity, urgency, feasibility (D5, D6)
    "ext":        customer extension fields (D8)
  }
}

  • A match isn't automatically training data. Under D10, a successful real-robot segment is evidence the situation is solvable: a reference for teleop or sim generation, and a corpus count. It can't fine-tune our LIBERO-tuned GR00T without converting it to that action space and camera setup. For our own policy, external search mostly says what to produce; producing still happens in sim or teleop.
  • Suggested order: a tier-1 dataset first (no new models; tests the search on data we didn't generate), then one tier-2 dataset with depth and calibration (DROID) to measure the cost of estimation, then tier 3, embedding-only.
  • Where an inverse dynamics model (IDM) helps. An IDM predicts actions between frames. It fills the action and proprioception gaps, which matter for turning matched video into training data (tier 3), not the object-pose gaps that the search needs. Tier 2 already has actions, so an IDM adds little there. On tier 3 the actions come out in the IDM's training embodiment, so human video needs retargeting from hand to gripper. One direct use for search: IDM-predicted gripper open/close gives tier-3 phase boundaries.
  • Phase segmentation without labels. Cheapest first:
    1. rules on proprioception (gripper events + eef speed), no training, for tiers 1–2;
    2. for tier 3, the same rules on a predicted gripper signal (IDM or hand-pose model);
    3. if rules fail, weak supervision: train a phase classifier on (vision + proprio) using labels from our sim segmenter, or zero-shot VLM labels on key frames, then distil. Expect a sim-to-real gap on the vision part; proprio features transfer better;
    4. unsupervised change-point detection or clustering of embeddings, as a last resort (its segments still need naming).
    Every route needs a small hand-labelled check set per tier (20–40 episodes) to measure accuracy, the same as P4b.
